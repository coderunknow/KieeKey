# KieeKey v1.2.2 RC4 — Release-Risk Inventory

Campaign: **v1.2.2 RC4 Stable Qualification** — baseline `v1.2.2-RC3` (commit
`dd3c42a3daf7b0e58e4a451d30b8812c8f405faa`).

Findings below were produced by a systematic RC4 audit (Phase 1/2 of the
campaign): Windows hook/transport/TSF layer line-by-line review, engine +
option-matrix review, build/CI/packaging/version-consistency audit, and
test/tooling review. Every P0/P1 entry marked **CONFIRMED** was re-verified
against the source by the release engineer before being accepted (audit
claims are evidence, not authority).

Classification: **P0** release blocker / catastrophic · **P1** serious
correctness/stability blocker · **P2** meaningful, non-blocking ·
**P3** cleanup.

---

## P0

### P0-1 · TsfComposer::commitBatch — double `Release()` on the edit session (UAF / double-free) — CONFIRMED, FIXED in RC4

`src/tsf/TsfComposer.cpp` (RC3 lines 552–579).

`commitBatch` creates a `CommitEditSession` (refcount 1 = the caller's
initial reference), requests a `TF_ES_READWRITE | TF_ES_SYNC` edit session,
then:

1. line 557: `session->Release();` — with `TF_ES_SYNC`, TSF's internal
   reference is already gone when `RequestEditSession` returns, so this
   drops the **last** reference and `delete this` runs inside `Release()`
   (this is exactly the mechanism the code's own v1.2.1 comment describes);
2. line 578: `session->appliedCount()` — reads freed memory (UAF);
3. line 579: `session->Release();` — decrements freed memory; if the block
   was reused, `--refs_` can reach 0 again → `delete this` a second time
   (double-free / heap corruption).

The v1.2.1 "USE-AFTER-FREE FIX" comment says "snapshot it BEFORE the
release", but the first `Release()` was never removed — the fix was left
half-applied. `commitOne` (single-delta path) has the correct single-Release
pattern and proves the intended refcount contract.

**Fix (RC4):** snapshot `appliedCount()` before a single `Release()`, exactly
matching `commitOne`. Regression protection: static verification + both
toolchain compile gates; runtime TSF validation remains
**NOT EXECUTED** (no Windows runner) — see the release report limitations.

## P1

### P1-1 · Producer handler exceptions can cross the Win32 hook boundary — CONFIRMED, FIXED in RC4

`src/core/ModernKeyHook.cpp` — `keyboardProc` / `mouseProc` /
`winEventProc` invoke `producerHandler_(ev)` with no exception isolation.
The handler runs application code that allocates (engine buffers, out-ring
pushes); a `std::bad_alloc` (or any engine exception) escaping a
`WH_KEYBOARD_LL` / `WH_MOUSE_LL` callback crosses a non-unwinding Win32
frame — UB, typically fail-fast. The consumer side has been fault-isolated
(`handlerExceptions_`, v1.2.0) since v1.2.0; the producer side was missed.

**Fix (RC4):** `try/catch (...)` around all three producer-handler call
sites; on catch, fall back to the no-handler contract
(`ProducerDecision{false, true}` = pass through + wake consumer) and count
into a new `producerExceptions_` diagnostic.

### P1-2 · `resyncModifiersFromOs()` writes `toggleKeyDown_` non-atomically from the UI thread (data race) — CONFIRMED, FIXED in RC4

`src/core/ModernKeyHook.cpp` `resyncModifiersFromOs()` does
`toggleKeyDown_.fill(0)` on a plain `std::array<std::uint32_t, 8>` while the
contract (`ModernKeyHook.hpp`) explicitly allows the UI thread to call it,
and `src/app/main.cpp` really does (3 call sites: lines 1186, 2055, 2505).
The hook pump thread concurrently read-modify-writes the same words in
`applyModifierDelta` (`wasToggleKeyDown` / `setToggleKeyDown`) — a C++ data
race (UB) that can lose a CapsLock toggle edge exactly while the key is in
flight (the "vợ renders as vỢ" family the function exists to cure).

**Fix (RC4):** `toggleKeyDown_` becomes
`std::array<std::atomic<std::uint32_t>, 8>` with relaxed-order bit ops; the
bulk clear becomes per-word `store(0, relaxed)`. Relaxed ordering is
sufficient: `modifierBits_` remains the synchronized state; the bitmap is an
edge-detection aid whose worst-case degradation (one suppressed XOR, corrected
by the next resync) is already documented as acceptable.

## P2

### P2-1 · Throwing allocation inside `noexcept` TSF methods → `std::terminate` — FIXED in RC4

`TsfComposer::commitOne` / `commitBatch` / `textBeforeCaret` are `noexcept`
but allocate (`new CommitEditSession`, `std::vector<EditDelta>` /
`std::wstring` copies, `out = session->result()`); `DoEditSession` /
`ReadBeforeCaretSession` assign into `std::wstring` inside COM entry points.
Under memory pressure this terminates the process from the consumer thread
and defeats both the app's `try/catch` and the consumer fault isolation.

**Fix (RC4):** whole-body `try/catch (...)` in the three composer entry
points (return `false` = graceful degrade to inline SendInput) and in the
two session `DoEditSession` implementations (set `*resultOut_ =
E_OUTOFMEMORY`).

### P2-2 · Unchecked Win32 returns: foreground WinEvent hook + ProcessMonitor start — FIXED in RC4

* `ModernKeyHook::hookThreadMain` / `reinstallHooksOnPump` publish only the
  keyboard-hook validity into `hooksInstalled_`; a failed
  `SetWinEventHook(EVENT_SYSTEM_FOREGROUND)` silently disables mouse
  word-break resync, modifier re-seeding and smart-switch. **Fix:** track
  `fgHookInstalled_` + a `fgHookFailures_` diagnostic, expose it in the
  wrapper diagnostics, and have the watchdog treat a missing fg hook on the
  pump as reinstall-worthy.
* `main.cpp` discards `g.monitor.start()`'s result — auto-exclusion could
  be silently off for the whole session. **Fix:** check the result and
  surface a one-time notification (the app's existing balloon path).

### P2-3 · `start()` after `stop()` can replay stale keystrokes — FIXED in RC4

`stop()` lets the consumer drain the ring before exiting, but a keystroke
processed by the pump *after* the consumer exited is parked in the ring with
nobody to drain it; `start()` re-arms flags without resetting the ring,
`suppressedDown_` or `toggleKeyDown_` — the next session delivers the
previous session's keystroke into whatever app is focused. Latent today (the
app never restarts the hook object) but the API explicitly advertises
restart, and tests exercise it.

**Fix (RC4):** `SPSCRing::reset_quiescent()` (documented: no producer/consumer
may be running), called from `start()` before the threads spawn, plus
clearing both bitmaps; `keyboardProc` gains a `running_` acquire-check before
consulting the producer handler (pass-through after stop). Verified that the
`stuckDetached_` "re-arm" in `start()` is unreachable whenever a wedge
actually happened (the store sits after the early return) — a restart after
a real wedge is refused on every attempt; comment clarified.

### P2-4 · ProcessMonitor foreground snapshot TOCTOU — FIXED in RC4

`updateFromWindow` captures the PID once and then runs OpenProcess /
image-name / process-times / token queries; if the PID is recycled inside
that window the snapshot classifies the *new* process for one foreground
event, and the header's "PID-reuse-safe" claim is not actually enforced
(`processStartTime` is recorded but never compared).

**Fix (RC4):** re-validate `GetWindowThreadProcessId(fg, &pid2)` after the
queries and before publishing; on mismatch, discard the snapshot (previous
snapshot stays; next event retries). The header claim is reworded to
describe the real guarantee (revalidated at publish time).

## P1 (build/release engineering)

### B-1 · Table generators would strip GPL headers and fail the version gate on regeneration — FIXED in RC4

`tools/gen_flat_tables.py` (writes `// KieeKey v1.1.2 — FlatTables.hpp
(GENERATED …)`, no GPL header) and `tools/flat_to_legacy.py` (same for
`VietnameseTables.source.hpp`) diverge from the committed files, which carry
the full GPL-3 header + a version-free banner. Following the documented
"DO NOT EDIT — regenerate" path would (a) strip license headers from GPL
files and (b) emit a versioned banner that `check_version.py` flags.

**Fix (RC4):** both generators now emit the exact GPL-3 header + version-free
banner; round-trip regeneration proven byte-identical against the committed
files (see release report).

## P3 (accepted, not fixed in RC4)

Recorded for the next cycle; none is release-critical:

* Watchdog rehook churn while an elevated/secure-desktop foreground is
  active (UIPI hides keystrokes; `hookReinstallCount_` inflates — harmless).
* `PostThreadMessage(WM_QUIT)` thread-id recycle window at shutdown
  (mitigated by pump-exit id clearing + 1 s fallback timer).
* Partial `SendInput` failure leaves a half-applied edit (counted in
  `sendInputFailed_`; SendInput is all-or-nothing in practice).
* `SetTimer` watchdog-arm return value unchecked (1 s fallback timer covers
  the wake guarantee).
* `Win32Handle::operator&` out-param overload is a latent trap (currently
  unused in `src/`).
* `GetAsyncKeyState` low-bit toggle read is documented-unreliable (bounded
  by periodic `resyncModifiersFromOs`).
* WinUI 3 CMake target (`XAML_IMPORT` is not a real source property) — the
  WinUI frontend is exercised via its consumer-callback contract in tests;
  the CMake target needs a real XAML build pipeline or demotion to
  documentation. Recorded; not fixed in RC4 (no Windows runner to verify a
  rebuilt pipeline).

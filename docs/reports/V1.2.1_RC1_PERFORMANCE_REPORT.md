## 2. Hypotheses Investigated

### H1: Adaptive spin uses RECENT MAXIMUM — a single outlier inflates future spin (CONFIRMED)

**Evidence (code audit):** `ModernKeyHook::consumerThreadMain()` in v1.2.0:
```cpp
std::uint64_t gapWindow[32]{};   // recent batch-gap ring (max over window)
const auto recentMaxGap = [&]() noexcept -> std::uint64_t {
    std::uint64_t m = 0;
    for (const std::uint64_t g : gapWindow) { if (g > m) { m = g; } }
    return m;
};
// ...
const std::uint64_t spinBudgetUs =
    std::clamp<std::uint64_t>(recentMaxGap() + recentMaxGap() / 4, 4, 200);
```

**Pathology:** Consider a user typing at 200 WPM (3ms inter-key gaps), then
pausing for 5 seconds to read something, then resuming at 200 WPM.

1. During the burst: gaps are ~3000µs, clamped to 200µs. Spin budget = 200µs. ✓
2. After the 5-second pause: the gap window still contains 3000µs entries
   (none of the 32 slots have been overwritten). The first key after idle
   arrives, is drained, and the gap since the last arrival is ~5,000,000µs.
   This is > 1,000,000 so it's ignored by `pushGap`. But the gapWindow still
   holds the old burst data.
3. Queue empties. Consumer calculates spin budget: `max(3000, 3000, ...) + 25%` = 3750µs, clamped to 200µs.
4. Consumer spins for 200µs on every empty dequeue cycle until the next key.

On a real system, this means after ANY pause, the consumer burns CPU spinning
for 200µs on every empty dequeue based on stale burst data. At a 5ms inter-key
rate, that's 4% of each inter-key interval wasted on unnecessary spinning.

**Fix:** EWMA with asymmetric alpha + idle decay. See §3.1.

### H2: THREAD_PRIORITY_TIME_CRITICAL on hook pump thread is unnecessary (CONFIRMED)

**Evidence:** The hook pump thread (`hookThreadMain`) installs hooks and runs
the `GetMessageW`/`DispatchMessageW` message loop. The LL callbacks
(`keyboardProc`, `mouseProc`) run on this thread but their work is:

1. Stamp tick (`GetTickCount` → atomic store)
2. Check self-injection filter (integer comparison)
3. Build KeyEvent POD (a few field assignments)
4. `try_push` to SPSC ring (one atomic load, one atomic store)
5. Optionally `SetEvent` (one kernel call, but only when consumer is parked)
6. Return (CallNextHookEx for pass-through)

This is O(1) work — approximately 200-500 ns total. `THREAD_PRIORITY_HIGHEST`
(2 below TIME_CRITICAL) is more than sufficient for a message pump. The
TIME_CRITICAL elevation on this thread preempted the foreground application's
UI thread without providing any latency benefit to the IME pipeline.

**Fix:** Drop to HIGHEST. See §3.2.

### H3: HIGH_PRIORITY_CLASS on the process is counterproductive (CONFIRMED)

**Evidence:** `Win32Wrapper::start()` sets `HIGH_PRIORITY_CLASS`:
```cpp
::SetPriorityClass(::GetCurrentProcess(), HIGH_PRIORITY_CLASS);
```

`HIGH_PRIORITY_CLASS` elevates EVERY thread in the process, including:
- The UI thread (message loop, settings dialog)
- The ProcessMonitor pump thread
- The watchdog timer thread
- Any std::thread spawned for async operations

The consumer thread (TIME_CRITICAL within a HIGH process) gets effective
priority ~31 (Windows scale). The foreground application's text rendering
thread typically runs at normal priority (~8). This creates scheduler
contention: the IME's elevated threads can preempt the very thread that
needs to paint the text the IME just committed.

The user-visible symptom: microbenchmarks show excellent internal latency,
but the text appears with visible delay because the foreground app's
rendering thread is starved.

**Fix:** Drop to ABOVE_NORMAL_PRIORITY_CLASS. The consumer alone at
TIME_CRITICAL is sufficient. See §3.3.

### H4: Lock-free queue has bottlenecks (DISPROVEN)

The Vyukov SPSC ring at capacity 4096 with cacheline-aligned slots is
correct and fast. `try_push` is one atomic load + one atomic store.
`try_pop_batch` amortizes the per-item atomic traffic. No improvement needed.

### H5: EditDrainBarrier has issues (DISPROVEN)

The hybrid spin+event barrier (200 iterations spin, then bounded 1ms event
wait) is correct and well-designed. The QPC-backed deadline prevents
timer-resolution inflation. No improvement needed.

### H6: timeBeginPeriod(1) causes unnecessary wakeups (DISPROVEN for this use case)

`timeBeginPeriod(1)` is called at process startup and released at exit. It's
needed for the EditDrainBarrier's 1ms wait budget (without it, the wait
stretches to 15.6ms). The watchdog WM_TIMER at 5ms also benefits. The cost
is a system-wide timer resolution increase, but this is a standard practice
for input-method applications and does not cause measurable battery impact
on modern Windows (per-process accounting since Win10 2004+).

### H7: Queue backpressure / overflow is problematic (DISPROVEN)

The ring capacity is 4096 events. At 200 WPM (1000 keys/min = 16.7 keys/s),
it takes 246 seconds of sustained typing without any consumer drain to fill
the ring. The consumer drains continuously. The overflow path (drop event,
count it, always wake) is correct and well-tested.

## 3. Changes Accepted

### 3.1 — EWMA Adaptive Spin with Idle Decay

**File:** `src/core/ModernKeyHook.cpp` — `consumerThreadMain()`

**Problem:** `recentMaxGap` over a 32-slot window with 200µs cap. A single
outlier gap (user pauses) stays in the window, inflating spin budget for all
subsequent keystrokes until 32 new gaps overwrite it. After idle, the
consumer spins on stale burst data.

**Change:**
- Replace 32-slot gap window with single EWMA value
- Asymmetric α: fast attack (¼) when gaps shrink, slow decay (¹⁄₁₆) when gaps grow
- Idle threshold at 50ms: when no batch arrives for 50ms, reset EWMA to floor (2µs)
- Spin cap reduced from 200µs to 100µs
- Spin budget = EWMA + 25% headroom, clamped [2µs, 100µs]

**Correctness argument:**
- The spin window is purely an optimization (the consumer always falls through
  to WaitForSingleObject when the queue stays empty). No correctness depends
  on the spin budget value.
- EWMA converges to the true inter-arrival rate faster than a max-window,
  because it tracks the TYPICAL gap, not the worst case.
- The idle reset ensures the consumer parks immediately after the user stops
  typing, which is the correct behavior (zero CPU waste).
- The 100µs cap still exceeds the kernel wake latency (1-3µs on Windows),
  so the common case (next key arrives within 100µs) is still served without
  a kernel wake.

**Impact:**
- During bursts: consumer stays hot (EWMA tracks burst rate). ✓
- After idle: consumer parks immediately (no CPU waste). ✓
- Single outlier gap: EWMA increases by (gap - ewma)/16 ≈ 6% of the outlier.
  A 1-second pause increases a 20µs EWMA by only ~62µs, which is within the
  100µs cap. Compare to the old algorithm where the entire window gets filled
  with 200µs (clamped) values. ✓

### 3.2 — Hook Pump Thread: TIME_CRITICAL → HIGHEST

**File:** `src/core/ModernKeyHook.cpp` — `hookThreadMain()`

**Problem:** TIME_CRITICAL on the hook pump preempted the foreground app's
UI thread. The hook pump does O(1) work per callback (enqueue + return).

**Change:** `THREAD_PRIORITY_TIME_CRITICAL` → `THREAD_PRIORITY_HIGHEST`

**Correctness argument:**
- Priority affects scheduling order, not correctness.
- The hook callback must return before `LowLevelHooksTimeout` (~300ms on
  modern Windows). At HIGHEST priority, the callback returns in <1µs.
- The consumer thread (which actually applies edits) remains at
  TIME_CRITICAL, so edit latency is unaffected.

### 3.3 — Process: HIGH_PRIORITY_CLASS → ABOVE_NORMAL_PRIORITY_CLASS

**File:** `src/core/win32_wrapper.hpp` — `Win32Wrapper::start()`

**Problem:** HIGH_PRIORITY_CLASS elevated every thread in the process,
creating scheduler contention with the foreground application.

**Change:** `HIGH_PRIORITY_CLASS` → `ABOVE_NORMAL_PRIORITY_CLASS`

**Correctness argument:**
- ABOVE_NORMAL still keeps the IME ahead of background work (compilers,
  downloads, Windows Update) that could cause scheduling delays.
- The consumer at TIME_CRITICAL within ABOVE_NORMAL gets effective priority
  ~23 (vs ~31 in HIGH). Still well above normal foreground threads (~8).
- The UI thread, monitor thread, and other non-critical threads now run at
  ABOVE_NORMAL, which is appropriate for their workload.

## 7. Real-World Impact Assessment

### What the user will notice:

1. **After idle, first key is responsive** — the consumer parks immediately
   after idle (EWMA resets to floor), so there's no unnecessary CPU spinning.
   The kernel wake adds ~1-3µs to the first key after idle, which is
   imperceptible.

2. **Under CPU load, typing feels smoother** — the process at ABOVE_NORMAL
   instead of HIGH means the foreground application's text rendering thread
   gets scheduled more fairly. The user sees text appear more consistently.

3. **CPU usage while typing is slightly lower** — the EWMA algorithm avoids
   the "stale max gap" problem where the consumer would spin for 200µs on
   every empty dequeue after a pause. With EWMA + idle decay, the consumer
   parks within 2µs after the queue empties post-idle.

4. **Burst typing is unchanged** — during a burst, the EWMA quickly
   converges to the burst rate and the consumer stays hot. The 100µs cap
   still exceeds the kernel wake latency, so burst keys don't pay the wake
   cost.

### What the user will NOT notice:

- No change in composition correctness (zero engine changes)
- No change in macro behavior
- No change in settings, UI, or features
- No change in TSF vs SendInput output policy
- No change in auto-exclusion behavior

## 9. Known Limitations

1. **Shared KVM host** — the E2E pipeline benchmark runs on a shared Linux
   KVM host, not real Windows. The burst-mode numbers include ~30µs of
   scheduler noise. Real Windows validation is needed for final performance
   claims (the v1.2.0 report documents the same limitation).

2. **Timer resolution** — `timeBeginPeriod(1)` is a system-wide setting.
   On Windows 11, per-process timer resolution is enforced. This report
   assumes Windows 10 2004+ or Windows 11.

3. **ARM64** — the priority changes apply identically on ARM64 Windows
   (same thread priority model). The EWMA algorithm is platform-independent.
   No ARM64-specific testing was performed in this cycle.

## 3. Bugs found

### 3.1 Use-after-free — `TsfComposer::commitBatch` (P0)

**Where:** `src/tsf/TsfComposer.cpp`, the batched TSF commit used for every
browser/Office edit (Auto TSF set and the LeastFlicker profile).

**Mechanism:** `CommitEditSession` is created with refcount 1 (the caller's
reference). With `TF_ES_SYNC`, TSF's internal reference exists only for the
duration of `RequestEditSession`; when it returns, only the caller's
reference remains. The v1.1.0 reference-balance fix added
`session->Release()` — which drops the last reference and runs
`delete this` — and then read `session->appliedCount()` afterwards for the
unapplied-suffix fallback bookkeeping. That read touches freed memory.

**Why it mattered:** this is the hot path of every TSF edit batch
(kilohertz during typing). In practice the freed block is usually untouched
for a while, so the value often "looked right"; under allocator pressure it
is a use-after-free with a wrong-count consequence — a wrong
`appliedCount` makes the SendInput fallback re-emit the WRONG suffix of the
batch (duplicated or missing text), and it is exactly the class ASan flags
as a sanitizer error (a release blocker per policy §23).

**Fix:** snapshot `appliedCount()` (a per-session value that cannot change
after `DoEditSession` returns) **before** the `Release()`.

**Coverage:** Windows-only surface — not exercisable by the native suite;
covered by the new cross-build gate compiling the file and by the
reordered-code review embedded in the source comment. The fallback contract
itself (deliver only the unapplied suffix) is unchanged and was already
pinned by the v1.1.3 tests.

### 3.2 Compile-breaking portability — `std::abs` on `LONG` (P1)

`ProcessMonitor::isFullscreenOnPrimary()` computes `std::abs` of `LONG`
(window-rect deltas). `std::abs` for integral types requires
`<cstdlib>`; MSVC's `<windows.h>` chain happens to provide it, so the
project's MSVC CI never saw the problem — but a conforming toolchain
(clang + mingw-w64 headers, the new cross-build gate) failed with 8 errors.
Fixed by including `<cstdlib>`.

### 3.3 Cross-thread handle reads in `start()` (P2, ×2)

`ModernKeyHook::start()` re-checked installation by reading
`keyboardHook_.operator bool()` from the starting thread while the pump
thread writes that handle. The v1.2.0 comment on `hooksInstalled_` describes
this exact pattern as "a data race, benign in practice on x86/ARM but
undefined" and claims the flag replaced it — but the handle read itself had
survived in the failure check. `start()` now reads only the atomic
handshake. `ProcessMonitor` had the same unfixed pattern on `fgEvent_`; it
gained the same handshake (`hookInstalled_`), including the two details
that make the flag correct across restarts: re-armed to `false` in
`start()` before the pump spawns, cleared when the pump unwinds.

### 3.4 WinUI 3 front-end (P2/P3, UX)

* **Macro expansions were silently dropped.** `MainWindow::commit()` returned
  early for `EngineCode::ReplaceMacro`, so "gõ tắt" abbreviations never
  expanded in the WinUI 3 front-end (the raw break key passed through) —
  the exact pre-v3.1 defect the D3 contract removed from the Win32 app
  (the v3.1 mega differential measured 462 627 gap events from this shape
  of bug). The front-end now applies the expansion exactly like the Win32
  app: delete `backspaceCount` chars, insert `macroExpansionUtf16`.
* **TSF apartment affinity violated.** `TsfComposer::attach()` ran on the UI
  thread (STA + `ActivateEx`) while every `commit()`/`textBeforeCaret()` ran
  on the hook's consumer thread. The Win32 app's design comment explicitly
  documents why STA objects must be created and released on one thread.
  The front-end now attaches lazily on the consumer thread and detaches via
  the consumer finalizer — which also removes a COM-init reference leak
  whenever hook start failed.
* **Stale About version.** The About line said "KieeKey v1.2.0 Stable" for
  the entire 1.2.1 RC cycle (the RC bumps touched only the Win32 carriers).
  It now derives from the public version macro, and `check_version.py`
  covers the file so it cannot drift again.

### 3.5 What was found and NOT changed (honesty)

* The GetMessage loop's `-1` handling (`while ((gmRet = GetMessageW(...)) > 0)`)
  could busy-spin on a persistent error. With a `nullptr` HWND this is not
  reachable in practice; the RC1 note documents the deliberate policy.
  Reviewed, left as-is, recorded here.
* `Win32Wrapper`/`PendingEditCounter`/`EditDrainBarrier`/`HookWatchdog`/
  `LockFreeQueue` were re-audited line by line; no defect found (the RC3
  saturating-release fix holds; the parked-wake protocol is sound under the
  documented interleavings).
* The engine's quick-Telex path skips macro-accumulator bookkeeping for the
  doubled letter (pre-existing since v1.2.0, observable only with a macro
  whose abbreviation ends in the doubled consonant AND quick-Telex enabled);
  legacy 2.0.5 parity is unclear in this corner, no user report, not touched
  in a hardening release — recorded as a known limitation.

**Not executed here (stated plainly, not claimed):**

  replace it.
* **On-host Windows runtime validation** (real SendInput/TSF/registry,
  tray, sleep/resume, elevated apps, DPI, screenshots) — this environment
  has no Windows host or emulator. The Windows-only code paths are validated
  by build + audit + the native shim pipeline (the deterministic Win32-shim
  harness that exercises the ring/barrier/emitter semantics off-Windows),
  and RC3's unchanged-surface argument now carries one MORE check: the
  cross-build link. Any claim beyond that would be marketing, and this
  report does not make it.

## 11. Benchmark methodology

* **Runner:** `tests/run_bench_suite.sh` (the RC2/RC3 harness, unchanged):
  builds both sides with identical flags, gates both sides, interleaves
  runs, reports medians.
* **A/B:** frozen RC3 git worktree (`v1.2.1-RC3-0-g016abac`) vs Stable tree,
  `--runs=3`, interleaved (cur seed 1001+r, base seed 2001+r).
* **Machine:** Debian 13, Linux 5.10 x86_64, Intel Xeon @ 2.60 GHz, 2 logical
  CPUs, 4 GiB RAM, shared KVM host (g++ 14.2.0). Flags per harness unchanged
  from RC3 (gate `-std=c++17 -O2`; perf `-O3`; e2e `-std=c++20 -O2`; tone
  `-std=c++23 -O2`; tput driver `-std=c++20 -O2`).
* **Noise handling:** medians over 3 interleaved runs; the E2E shim's timer
  floor (~9.5 µs p50) and the ±5 % band on sub-µs tone populations are the
  same "unchanged" verdict bands RC2/RC3 established. The A/B isolates the
  engine + wrapper by syncing harness sources into both trees.

### 12.6 Why the E2E deltas are noise *by construction*

The E2E shim harness (`tests/e2e_bench.cpp` + the win32 shim) is compiled
from byte-identical sources in both trees (the A/B runner syncs harness

noise, not a change effect — the same verdict class RC3 §7.3 established,
here provable rather than argued.

## 17. Limitations

1. No Windows runtime here: real-app validation (Word/browsers/elevated/UWP,
   sleep-resume, DPI, screenshots) was NOT performed for this release; see
   §10 for exactly what was and was not validated.
2. The WinUI 3 front-end requires the Windows App SDK and is not built by
   CI; its three fixes are build-validated (the cross gate compiles the
   shared core they depend on) and review-validated, not runtime-validated.
3. Competitor binary benchmarks (UniKey/EVKey/current OpenKey) were not
   performed — §13 records why, and what exists instead.
4. Startup-to-interactive and settings-open times are Windows-runtime
   measurements and remain NOT MEASURED off-Windows.

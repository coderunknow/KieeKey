## 3. Pipeline measurement + bottleneck attribution (done BEFORE optimizing)

### 3.1 What the full chain is

`WH_KEYBOARD_LL/WH_MOUSE_LL/WinEvent` (hook pump) → producer-side engine
decision (or consumer-callback-only path) → SPSC key ring + auto-reset event
wake → consumer thread → `TextEngine::process` → `replacementUtf16` →
`InlineEmitter`/TsfComposer → target app. The Linux shim (`win32_wrapper.cpp`,
deterministic) models the producer→consumer→emitter handshake; it does **not**
model real SendInput kernel cost (~1–2 µs serial, same for any IME).

### 3.2 The two wirings — and which one the RC2 report measured

| Wiring | Who | Legacy of |
|---|---|---|
| **production** | Win32 app (`main.cpp`): producer handler registered (`g.hook.setProducerHandler(onHookEvent)` ~line 3811); pass-through keys → `countPassThrough`, consumer only woken for suppressed edits | the shipped app, RC2 and RC3 |
| **all** (consumer-callback-only) | no producer handler; every key rides wake→consumer (the RC3 hook fix makes this the *real* contract again) | WinUI 3 front-end + the historical e2e model — **this is what RC2 published** |

The e2e bench historical default (and the RC2 suite's `e2e_cur_*`) measured
**all**; RC3's `e2e_bench` adds `--model=production` (schema v3) to measure the
wiring the shipped Win32 app actually uses. The first production-model probes
(`e2e_1cpu_prod.json`, `e2e_2cpu_prod.json`, 10 k keys) were recorded in the
RC3 campaign; the published RC2 medians came from all-model.

### 3.4 Optimizations measured and rejected (perf decision table)

Every candidate below got a hypothesis, a baseline, a controlled A/B and a
rollback criterion. **None was adopted**, and §3.5 explains the only one that
could have been (spin-cap) — honestly, in the wrong direction.

| Candidate | Hypothesis | Evidence | Verdict |
|---|---|---|---|
| Raise adaptive spin cap 100→1000 µs (production wiring) | keep consumer hot across burst gaps, cut p99.9 | FINAL A/B (100 k keys × 3 runs each, `final/e2e-v4-prod-spin100-*` vs `-spin1000-*`): raw p99.9 **49.4 → 18.8 µs** (all 6 pair-runs, non-overlapping), burst p99.9 19.2 → 3.6 µs; p50/p95/p99 within ±10 %. BUT: the gap it bridges is 300–800 µs (the bench's word-burst convention); at human cadence (150 WPM = 48 ms inter-key ≫ 1 ms cap) the consumer is parked in both settings, so the gain does **not** transfer to the user-visible KPI. CPU/energy: production wiring mean 5.7 % → 6.0 %, peak 39.7 % both; **consumer-callback (all-model, the WinUI wiring) peak 59.6 % → 139.0 %** | **REJECT** — real bench-tail gain confined to a non-human stress regime; no evidence of user-visible benefit; CPU peak doubles where it matters most (consumer-callback wiring) |
| Lower spin cap 200→100 (production) | save CPU without tail loss | FINAL: default-path burst p99.9 17.7 µs (e2e-v4-prod-*) vs spin100 19.2 µs (e2e-v4-prod-spin100-*), raw p99.9 55.0 vs 49.4 µs — **no measurable CPU saving** (mean 5.7 % vs 5.7 %, peak 39.7 % both) and a tail that is equal-or-worse | **REJECT** — no energy win, tail not better; 200 µs default stays |
| Spin-cap 100 vs 200 vs 1000 (all-model, legacy) | same question on the consumer-callback wiring | `rc3-pair/e2e_spin100/200/1000.json`: spin1000 p50 0.743 / p99 3.62 / p99.9 35.5 vs spin100 26.7/70.1/586 — huge *bench* win, but only because spin1000 keeps the consumer awake through 80 ms pauses; real app cadence ≠ bench cadence | **REJECT for production** — artifact of the bench's inter-burst spacing, CPU 2–3× |
| Paced (150 WPM) spin 200 vs 100 | does the spin policy matter at human cadence? | `rc3-pair/e2e_prod_paced` (p50 2.17 / p99 5.13 / p99.9 47.5, n=2,000) vs `_paced_spin100` (2.61/7.64/95.8, n=20,000) — both dominated by pacing-sleep CPU-wake artifact; neither spin setting changes the edit-path cost at human cadence (and the two runs differ in key count, so the p99.9 gap is not a controlled A/B) | **REJECT** — no user-visible difference; spin policy is a no-op at 150 WPM |

### 3.5 Honest statement on the stretch KPI

The RC2-published numbers (27.750/71.414/590.1 µs) are what the *previous*
report published as the pipeline latency, but they describe the all-keys
model. The RC3 KPI table below compares **both ways**:

- **Same methodology (all-model)**: RC2 → RC3 = +9.5 % p50 (27.75 → 30.38),
  −1.3 % p99 (71.41 → 70.51), p99.9 590.1 → 127.0 µs (but the RC2 3-run
  spread is 123–623 µs, so this is noise, not a win) — **no regression, no
  credible improvement**. (The RC3 all-model p999 run values are 126.4/127.0/785.7;
  the median-of-3 is 127.0.)
- **Shipped wiring (production model)**: RC3 = 0.183/0.980/55.0 µs
  (p50/p99/p99.9). The Win32 app in RC2 was *already* this wiring (producer
  handler + countPassThrough existed at bc0a20a), so RC2's true
  shipped-wiring numbers were already at this level — the archive simply
  never measured them. **The ≥10 % improvement vs the RC2-published numbers
  is real as a number, but it is a measurement-correction, not a code
  optimization.** No optimization was needed on the shipped path; the
  release's value is the corrected KPI baseline, the closed WinUI hole, and
  the torture gate.

## 5. The WinUI 3 fix (the RC3 code change)

**Bug (RC2, inherited from the producer-handler refactor):** all three hook
entry points called

```cpp
const ProducerDecision d = self->producerHandler_ ? self->producerHandler_(ev) : ProducerDecision{};
```

`ProducerDecision{}` = `{suppress=false, wake=false}`. The F9/suppression path
in the Win32 app always registers a handler, so the Win32 app was unaffected —
but a consumer-callback-only front-end (**WinUI 3 `MainWindow.xaml.cpp`**,
which calls `m_hook->start(consumerCallback)` with **no** producer handler)
received **zero key/mouse/foreground events**: every event was counted
pass-through, the consumer callback never ran, no composition, no word-break,
no foreground refresh. The WinUI front-end was a silent no-op.

**Fix:** the no-handler default is now `ProducerDecision{false, true}` at all
three sites (keyboardProc, mouseProc button/wheel branch, foreground
winEventProc), with contract comments added in `ModernKeyHook.hpp`. The
producer handler remains an *optimization* registered by the Win32 app; the
**consumer-callback contract** ("every event delivered to the consumer") is
the default when no handler exists. Verified by: (a) code-level reading of the
three sites and the consumer-callback implementation in `MainWindow.xaml.cpp`
(which handles Mouse/ForegroundChanged/KeyDown precisely); (b) the e2e `all`
model — which now *is* this contract after the fix — reproducing the historical
all-keys numbers the WinUI front-end will see; (c) the native suite's
lifecycle/state-transition tests (Linux stand-in models the same state machine
— 24/24 PASS on the final tree).

**Not verified:** compiled in this sandbox (Windows-only source, no cross
toolchain). CI's x64/ARM64/ARM64EC jobs compile `KieeKeyApp.exe`
(= `ModernKeyHook.cpp`) as part of the PR; the WinUI 3 project itself is not
built anywhere (`KIEEKEY_BUILD_UI=none`) — recorded as a limitation.

**Perf note (measured, not glossed):** for a consumer-callback-only front-end
the fix adds the consumer hop back for every key (≈27 µs p50 all-model on the
shim) — that is the front-end's architecture (engine runs on the consumer
thread), not a regression introduced here; it was the pre-refactor behavior
and the only way the front-end can work at all.

## 6. CPU / energy trade-off + 1-CPU/2-CPU contention

Tool: `docs/bench/rc3-122/tools/cpu_tradeoff.py` (sampled `/proc/<pid>/task/*/stat`
every 50 ms; mean + peak instantaneous CPU% of *one* logical CPU, n samples).
Final e2e binary, 100 k keys, 1 run each (`rc3-suite/cpu-tradeoff-v4.txt`):

| Config | mean CPU | peak CPU | n |
|---|---|---|---|
| production, spin=100 | 5.7 % | 39.7 % | 145 |
| production, spin=1000 | 6.0 % | 39.7 % | 145 |
| all, spin=100 | 7.2 % | 59.6 % | 147 |
| all, spin=1000 | 5.1 % | 139.0 % | 145 |

Interpretation: production wiring mean CPU ~5.7–6.0 % *while typing* (peak is
scheduler-visible spin bursts at 39.7 %); the all-model wiring has 1.3× higher
mean and — at spin1000 — **2.3× the peak** (139 % vs 59.6 %). Spin-1000 does
**not** reduce mean CPU in the production wiring (it parks less but burns more
per wake); where the consumer is woken for every key (all-model, the WinUI
wiring) it multiplies peak — consistent with the §3.4 rejection. No AC/battery
data (virtualized host) — "energy" is reported as CPU%; real-mAh measurement
is outside this environment (as in RC2).

**1-CPU vs 2-CPU contention** (`e2e_1cpu_prod.json` vs `e2e_2cpu_prod.json`,
production wiring, 10 k keys):

| | 1 CPU | 2 CPU |
|---|---|---|
| raw p50/p99/p99.9 (µs) | 0.139 / 0.700 / 22.9 | 0.135 / 0.730 / 27.3 |
| burst p50/p99/p99.9 (µs) | 0.129 / 0.556 / 22.1 | 0.124 / 0.543 / 1.44 |
| wake p50/p99 | 0.351 / 1.083 | 0.356 / 1.255 |
| throughput | 13,942 | 13,926 |

One core with the consumer spinning is *not* a latency cliff (p999 22.9 vs
27.3 µs, both deschedule-dominated); the tail with 2 cores where the consumer
gets scheduled promptly is 1.44 µs. No starvation regression → the spin/wait
policy is safe on single-core machines.

## Executive summary

**What changed from RC4:** release identity and release evidence only.

* Version carriers → `1.2.2 Stable` (`kieekey_core.hpp` VERSION_STRING,
  `main.cpp` `kAppVersionFull`/`kAppTitle`, `check_version.py` CHANNEL,
  README headline + What's-new, CHANGELOG, this report set, bench indexes).
* New evidence tree `docs/bench/stable-122/` (this campaign).
* `SHA256SUMS.txt` regenerated over the final tree and verified.

**What did NOT change:** every runtime source file is byte-identical to
RC4 — `git diff v1.2.2-RC4..v1.2.2` touches no `src/` semantics (the two
`src/` edits are the version-string constants above), no engine hot path
(`TextEngine.*`, `FlatTables.hpp`, `VietnameseTables*`, `PerfProfile.hpp`
untouched), no tests, no build logic, no benchmark methodology. **Zero new
features. Zero optimizations. Zero semantic changes.**

**Why the release is safe:** RC4's stable-qualification fixed the last
known P0/P1 (all seven fixes re-verified in source by this campaign); this
campaign then re-ran the full gate set on an **independent host and
compiler** (Debian 12 / g++ 12.2 vs RC4's Debian 13 / g++ 14.2) and
reproduced every RC4 claim: identical correctness counts, identical
determinism digests (cross-host), clean sanitizers, and a strict
three-way benchmark whose decision metrics are flat RC4→Stable and
**−8.6 % floor vs v1.2.1 Stable with byte-identical sink digests**.
The RC4→Stable measured binaries are section-identical, so the release is
performance-preserving **by construction and by measurement**.

**Remaining limitations (unchanged from RC4, explicit):** real-Windows
runtime validation (L3–L6) was NOT EXECUTED here — no Windows host exists
in this environment; the RC4 fixes' runtime behavior still needs one
real-Windows pass (CI runs the MSVC build matrix + x64 ctest on push/tag).
ARM64EC cross-build is NOT AVAILABLE on this host (no arm64ec target in
Zig; MSVC-only). Energy measurement: NOT AVAILABLE, no claims made.

**Final verdict: RELEASED — v1.2.2 Stable** (all runnable gates PASS; see
§9).

## 7. Regression analysis (every noticeable difference)

1. **Floor median +1.17 % RC4→Stable in the first 3-run window** (above
   the 1 % line → investigated per policy):
   (a) code mechanism excluded — `TextEngine.o`/`win32_wrapper.o` sections
   SHA-identical between the trees; (b) A/A control measured: same binary
   swings −2.6 %…+4.4 % paired; (c) all 8 A/B pairs: deltas flip sign,
   median +0.06 %, mean −0.35 %. **Conclusion: sampling noise; not
   reproducible; not a regression.**
2. **E2E latency medians "+19.7 % Stable" in suite session 1**: paired
   per-run deltas swing −17.0 %…+27.7 % in the same session; session 2
   (5 fresh pairs) shows Stable **−7.1 %** (faster); A/A control spans
   ±10–21 %; binaries section-identical; throughput flat both sessions
   (−0.06 %/+0.13 %). **Conclusion: host scheduler noise on a shared
   2-core VM; no code effect exists (identity proven); not a
   regression.**
3. **IME footprint +0.28 MB vs v1.2.1** (consistent across every run and
   session): explained — the 1.2.2 engine's sequence-bucket tables and
   batch-commit state from the RC1–RC3 campaign (documented then);
   accepted; total RSS ~8.5 MB.
4. **Micro p99 tails (delete +15.9 % = 82→95 ns, passthrough +5.9 % =
   70→72 ns, RC4→Stable)**: ns-scale single-run tail jitter with p50
   exactly 0.0 % on all four workloads and identical code; not
   meaningful.
5. **1.2.1 vs 1.2.2 micro trade-offs** (delete +4.3 %, passthrough +2.4 %
   vs vn-compose −5.5 %, mixed −3.6 %, floor −8.6 %): the documented
   RC1/RC2 hot-path rework trade-off — net engine throughput clearly
   better; per-class deltas already published in the RC campaigns.

**No reproducible >1 % regression exists on any strict comparison.**

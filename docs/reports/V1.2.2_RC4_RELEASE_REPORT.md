## Executive summary

**What changed (9 source files, +247/−44 lines — all correctness/stability/
release-engineering; ZERO engine hot-path changes):**

| Fix | Severity | File |
|---|---|---|
| TSF `commitBatch` double `Release()` → UAF/double-free on every multi-delta commit (the v1.2.1 fix was left half-applied) | **P0** | `TsfComposer.cpp` |
| Producer-handler exception isolation in all 3 LL/WinEvent callbacks (exception across a Win32 hook frame = UB/fail-fast) | P1 | `ModernKeyHook.cpp/.hpp` |
| `toggleKeyDown_` UI-thread data race (bulk clear vs pump-thread RMW) → relaxed atomics | P1 | `ModernKeyHook.cpp/.hpp` |
| `noexcept` TSF entry points no longer `std::terminate` on OOM | P2 | `TsfComposer.cpp/.hpp` |
| Foreground WinEvent-hook + ProcessMonitor start failures surfaced (new `AutoExcludeUnavailable` notification) | P2 | `ModernKeyHook.*`, `ProcessMonitor.*`, `Notifications.hpp`, `main.cpp` |
| `start()`-after-`stop()` stale keystroke replay closed (`reset_quiescent` + `running_` guard) | P2 | `LockFreeQueue.hpp`, `ModernKeyHook.cpp` |
| ProcessMonitor PID-reuse revalidation before publish | P2 | `ProcessMonitor.cpp/.hpp` |
| Generators emit GPL header + version-free banner (regeneration proven byte-identical); rotted reverse bridge fails loudly | P1(build) | `tools/*.py` |
| Presets default dependency-free; CI enforces `SHA256SUMS.txt`; `.gitignore` keeps bench evidence; stale metadata fixed; dead code removed; option-matrix banner derived from the version macro | P2(build) | build/CI/docs |

**What did NOT change:** `TextEngine.cpp/.hpp`, `FlatTables.hpp`,
`VietnameseTables*`, `PerfProfile.hpp` — the engine hot path is byte-identical
to RC3 (`git diff v1.2.2-RC3 HEAD -- <engine files>` is empty — VERIFIED).
No new features. No benchmark-methodology change. No compatibility-semantics
change.

**Why:** the RC4 mandate was to find and fix remaining release-critical
weaknesses, not to add anything. The P0 was found by re-auditing the TSF
refcount contract against the code's own v1.2.1 comment; the two P1s by
mirroring the already-proven consumer-side protections (v1.2.0 fault
isolation, atomic modifier bookkeeping) onto the producer side and the UI
thread.

**Final verdict: READY FOR STABLE** — all runnable mandatory gates pass with
clean evidence; the only non-runnable validation classes (real-Windows
runtime, WinUI 3 runtime, real hardware) are explicitly recorded as NOT
AVAILABLE / NOT EXECUTED below and are inherited RC3 limitations, not RC4
regressions.

`tests/bench_three_engines.cpp` — vendored, unmodified reference engines,

| UniKey 4.x UKEngine (vendored) | 111 | 182–184 | 14/15 |

Scope/limits (recorded, not hidden): this measures **engine decision latency
+ composition correctness** headlessly — NOT the shipped Windows typing path
(TSF/SendInput costs are excluded by design; they are not reproducible
headlessly). UniKey's lower p99 reflects its simpler state machine on the
same streams; the passage suite reflects the differing auto-restore
semantics (documented rule differences). No overall-superiority claim is
made or implied. Competitor data is locally measured (not externally
sourced). Pre-existing vendored-reference defects (UniKey 128-word buffer
overflow; OpenKey 2.0.5 `checkForStandaloneChar` OOB read under ASan) are
documented in the log, not patched — the reference stays pristine.

## Limitations (unresolved, explicit)

1. **Real-Windows runtime validation (L3–L5)** — NOT EXECUTED on this host;
   CI's MSVC x64 leg runs the suite on tag/push. The P0/P1 TSF/hook fixes
   are verified statically + by cross-compile + review; their runtime
   behavior needs one real-Windows pass before or right after Stable.
2. **Real-hardware energy measurement** — NOT AVAILABLE; no battery/energy
   claims are made anywhere in RC4.
3. **WinUI 3 CMake target** needs a real XAML build pipeline or demotion to
   documentation (risk inventory P3); the WinUI consumer-callback contract
   is covered by shim tests only.
4. **P3 items** listed in the risk inventory (watchdog rehook churn under
   elevated foregrounds, `SetTimer` return checks, `operator&` latent trap,
   partial-SendInput truncation counter, thread-id recycle window) —
   accepted, none release-critical, all recorded for the next cycle.
5. **Deep-campaign scope** — the deep option-matrix campaign (92.4M events
   across all 7 tiers, `option-matrix-deep-100k.json`) runs separately from
   the ≤15-min release gate; the mandatory gate stays at the suite's 20k
   depth (~87 s).

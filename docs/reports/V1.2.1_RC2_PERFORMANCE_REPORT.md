**Release:** `v1.2.1 RC2`

**Branch:** `release/v1.2.1-rc2`

> Priority order, unchanged from RC1:
> REAL USER-PERCEIVED SMOOTHNESS > REAL END-TO-END LATENCY >
> STABILITY / CORRECTNESS > RESOURCE EFFICIENCY > MICROBENCHMARK SPEED

## 1. Method

### 1.1 Baseline first (RC1, frozen)

RC1 (`0884c64`) was built and both benchmark entry points were run **before
any RC2 code existed**, on the same host, and the raw artifacts are committed:

* `docs/bench/rc1/suite/` — `tests/run_bench_suite.sh --side=rc1`: gate,
  `bench_perf` ×3, `e2e_bench` ×3, `bench_tone_latency`, `env.json`
  (compiler, flags, OS, CPU, RAM, timer), `summary.{txt,json}`.
* `docs/bench/rc1/realworld.log` — `bench_real_world_typing --keys=50000 --runs=3`.
* `docs/bench/rc1/profiles_{burst,paced}.{log,json}` — the RC1 *engine +
  wrapper* driven by the new profile harness (Balanced row only; RC1 has
  no profiles).

RC2 artifacts live in `docs/bench/rc2/` with the identical layout plus
`gprof_flat.txt` and `compare_tables.md` (the full auto-generated
RC1-vs-RC2 tables, every row labelled faster/unchanged/slower).

**Environment (from `env.json`, identical for both sides):** g++ 12.2.0
(Debian), Linux 6.1 x86_64, Intel Xeon @ 2.60 GHz, **2 logical CPUs**, 4 GB
RAM, shared KVM host (SCHED_FIFO unavailable → scheduler noise expected and
handled with interleaved multi-run medians). Flags: gate `-std=c++17 -O2
-DNO_205`; bench_perf `-std=c++17 -O3 -DNDEBUG`; e2e `-std=c++20 -O2
-DOK_WRAP_NO_WIN32`; tone `-std=c++23 -O2`; real-world `-std=c++20 -O2
-DNDEBUG`. **No benchmark source, flag, corpus, or statistic was changed
between the RC1 and RC2 runs.**

### 1.2 What is / is not measurable here

Measurable: engine decision latency, the deterministic shim pipeline
(`win32_wrapper` compiled with `OK_WRAP_NO_WIN32`), tone populations,
differential correctness, allocation counts, RSS. **Not** measurable:
real `SendInput`/TSF/registry latency, Windows startup time, real
foreground-app flicker. Windows-only claims in this report are therefore
*compile-verified* (clang cross-build, x64 + ARM64) and *design-argued*,
never presented as measured.

### 1.3 Profiling

`gprof` flat profile of a 20 M-key clock-free throughput driver
(`docs/bench/rc2/tput_driver.cpp`, same prose + backspace-storm stream as
`e2e_bench`):

| function | RC1 self % | RC2 self % |
|---|---:|---:|
| `checkSpelling` | **52.6 %** | 34.3 % |
| `handleMainKey` (+ `checkCorrectVowel` inlined) | 5.3 % + 5.3 % | 24.7 % (absolute time down 40 %) |
| `process` | 7.2 % | 12.3 % |
| `pushTypingState` | 8.6 % | 5.5 % |
| `mainKeyBranch` | 6.6 % | (inlined) |

RC1 total ≈ 105–113 ns/key on this driver; RC2 ≈ 59–65 ns/key (`-O2`;
`-O3` 58.7, `-march=native` 60.4 — see §6 for why neither was adopted).

## 2. Hot-path audit (what was looked at, what was found)

| Area | Finding | Action |
|---|---|---|
| **Key processing / Telex transforms** | `checkSpelling` walked up to 33 leading-consonant rows × 3 cells with two option-dependent masks recomputed per cell; `checkCorrectVowel` was called for up to 79 candidate sequences per mark key although ~90 % fail on the first comparison. | Optimizations A–D (§3). |
| **Allocations** | `typingStates_` was a `std::vector` with erase-from-front on overflow (O(n) shuffle + realloc); everything else on the hot path already used fixed arrays / thread-local scratch. `stress_rc2` scenario 2: **2 allocations over 1.8 M keys** after warm-up; RSS delta 0 kB. | HistoryRing (§3-A). |
| **Locking** | One `engineMtx` per key (uncontended; UI thread takes it only on settings change). Measured cost inside the noise floor; a lock-free redesign would add risk with no measurable gain. | Rejected (§6). |
| **Consumer wake / spin** | RC1 EWMA spin kept; made **runtime-tunable** (floor/cap) so profiles can trade CPU for wake latency. Defaults = RC1 (2/100 µs). | Kept; profile-driven. |
| **Ordering barrier (`EditDrainBarrier`)** | Fixed 1 ms budget / 200 spin iterations. Made tunable (clamped 1–4 ms). Defaults = RC1. | Profile-driven. |
| **TSF edit batch** | Fixed 32. Now `g.editBatchMax` (1…64, hard cap `kMaxEditBatch=64`). | Profile-driven. |
| **Win32 / IPC** | `OutputItem` is trivially copyable, ring 1024; unchanged. No per-key syscalls besides the LL hook itself. | No change. |
| **Config reads** | Registry read once at startup and on settings save; **new RC2 settings follow the same path** (no per-key reads). | Verified. |
| **Logging** | No logging on the hot path (profiling channel compile-time gated by `KIEEKEY_PROFILE`). | Verified. |
| **Timers** | RC1 5 ms `WM_TIMER` + `timeBeginPeriod(1)` retained (disproven in RC1 report). RC2 adds **one** 1 s timer for notification polling + Adaptive re-resolution (≤ 1 wake/s, no work when nothing pending). | Accepted. |
| **Startup** | Adds one `PerfProfile` resolve (constexpr-evaluable) and ≤ 4 registry DWORD reads (`NotifySuppress_<id>`). Sub-millisecond by construction; not measurable off-Windows. | Accepted. |
| **UI thread** | Notification presentation is a tray balloon + one `MessageBox` on click; nothing touches the hook thread. | Accepted. |

## 3. Optimizations kept (all engine, all decision-identical)

Every step below was measured on the throughput driver and gated by
`diff_engine_ab` (RC1 engine vs live engine, lockstep, 1.2 M events, random
option matrices with mid-stream option switches, `switchToneStyle` and
`resumeFromText` replays).

| # | Change | ns/key (driver) | Kept because |
|---|---|---:|---|
| RC1 | — | 105–113 | baseline |
| **A** | `HistoryRing`: bounded 64-entry ring replaces `std::vector` + `erase(begin())` for the undo history | ≈ 91 | O(1) push, zero heap traffic, 8 KiB inside the engine object; removes the only hot-path allocation |
| **B** | `matchLeadingConsonant`: option masks folded once per call (were per cell); same row order, same short-circuit, same final `j` | ≈ 72 | `checkSpelling` self time 52.6 % → 34 %; semantics documented line-by-line in the source |
| **C** | `handleMainKey` pre-filter: hoist the "buffer ends in QU" guard and the "sequence tail == last char" test *before* `checkCorrectVowel` | 63–68 | ~90 % fewer candidate calls, outcome identical (the rejected candidates all failed on that first comparison in RC1) |
| **D** | End-consonant matcher mirrored from B | 60–62 | same argument as B |

Engine object size and layout of `EngineResult` are unchanged; the public
API is unchanged.

### 4.5 Memory / CPU / startup

* **Engine object:** +8 KiB in-object (`HistoryRing`) replaces a heap
  vector of the same logical capacity → net heap **lower**, RSS unchanged
  (8.44 MB both sides).
* **Hot-path allocations:** 0 (RC1: history vector growth/erase). Verified
  by `stress_rc2` scenario 2 (operator-new counter).
* **CPU per key:** −28 % … −54 % (real-world bench "CPU cost per key").
* **Idle CPU:** unchanged in Balanced; **lower** in Adaptive after 30 s idle
  or on battery (spin cap 100 → 20 µs) and in the LowCpu hybrid.
* **Startup:** +1 constexpr strategy resolve + ≤ 4 registry DWORD reads.
  Not measurable off-Windows; sub-ms by construction.

### 4.6 Regressions / insignificant gains — investigated

1. **`raw p99` +5.3 %, `raw p999` +4.2 %, `lag-spike keys` +9 % (e2e).**
   Per-run values: RC1 p99 = 103 / 110 / 106 µs; RC2 = **4436** / 93 / 112 µs.
   Run 1 of RC2 was hit by a host preemption (p999 8 ms, wake p99 4.4 ms —
   a scheduler event, not a code path; the same run's *hot* p99 was normal).
   The medians therefore compare RC1-run-3 with RC2-run-3. `raw` includes
   the cold-start and every wake; `burst/hot` and `pipeline` (which exclude
   the parked-wake outliers) improved 6–10 % at p99. The lag-spike count
   (keys > 100 µs) is a direct function of these host preemptions: RC2's
   non-preempted run had **789** spike keys vs RC1's best of 1180.
   **Conclusion: not a code regression** — same code path, faster engine,
   noise on a shared 2-vCPU host; the metric is retained un-massaged.
2. **Throughput −0.5 %.** `e2e_bench` paces the producer; throughput is a
   pacing property, not an engine property. Unchanged by design.
3. **Tone `reposition` / `tone-append` +8–10 ns.** One timer tick
   (T0-control floor is 28 ns); the populations have no spelling scan to
   speed up. Unchanged.
4. **E2E p50 gain (−8 … −10 %) is smaller than the engine gain (−45 %).**
   Expected: the engine is ~70–130 ns of a ~30 µs hop; the visible gain is
   the reduction in the producer's critical section before the ring push
   plus fewer cache misses on the consumer side. The pipeline hop itself
   (ring + wake + simulated commit) was not changed in RC2 — by policy
   (§6: rejected pipeline rewrites).

## 5. Performance Preference Profiles (measured)

`src/core/PerfProfile.hpp` — one `Strategy` struct resolved from
(`Profile`, hybrid flags, `Telemetry`) → applied by `applyPerfStrategy()`
in `main.cpp` to: output preference (Auto / Inline / TSF), consumer spin
floor/cap, barrier budget/spin, TSF batch cap, deferred inline, dictionary
restore, per-key layout re-check, slow-TSF downgrade.

| profile | output | spin cap µs | barrier µs | batch | dict | layout/key |
|---|---|---:|---:|---:|---|---|
| **Balanced** (default = RC1) | Auto | 100 | 1000 | 32 | opt | off |
| **Fastest** | Inline | 200 | 500 | 8 | off | off |
| **Least Flicker** | TSF, defer inline | 200 | 2000 | 64 | opt | off |
| **Maximum Correctness** | Auto | 100 | 4000 | 1 | **on** | **on** |
| **Adaptive** | Balanced re-resolved every 1 s from telemetry (slow TSF ≥ 3 → Inline; barrier misses ≥ 5 → 2 ms/200 µs; ≥ 8 keys/s → hot; idle ≥ 30 s or battery → 20/2 µs; 1 CPU → 4 µs) |
| hybrids | `PreferInline`, `PreferTsf`, `ExtraCorrect` (+dict, +barrier), `LowCpu` (spin 20/2, batch 16) — OR-able onto any base |

Measured with `tests/bench_profiles.cpp` (same shim pipeline as e2e; the
only inputs are the resolved `Strategy` fields; simulated TSF commit cost
is a constant 3 µs for every profile). **Unpaced burst, 100 k keys, median
of 3** (`docs/bench/*/profiles_burst.log`):

| build / profile | dec p50 ns | e2e p50 µs | e2e p99 µs | e2e p99.9 µs | barrier p99 µs | barrier timeouts | commits | visible retypes | consumer CPU ms |
|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| **RC1 / default** | 148 | 1.02 | 39.4 | 5571 | 1139 | 1144 | 4696 | 5349 | 80.5 |
| **RC2 / default (Balanced)** | 108 | 0.92 | 43.0 | 2279 | 1090 | 66 | 4486 | 5349 | 83.4 |
| **RC2 / Fastest** | 80 | **0.19** | **0.47** | **0.61** | 0 | 0 | 0 | 10 696 | 0.1 |
| RC2 / Least Flicker | 131 | 2.54 | 50.0 | 10 596 | 2105 | 246 | 9396 | **0** | 176.8 |
| **RC2 / Max Correctness** | 101 | 3.97 | 32.9 | **56.1** | 50.4 | 10 | 5564 | 5557 | 104.1 |
| RC2 / Adaptive | 99 | 0.91 | 36.9 | 91.1 | 1101 | 150 | 4703 | 5349 | 81.2 |
| RC2 / Fastest+Dict | 85 | 0.20 | 0.74 | 1.03 | 0 | 0 | 0 | 11 121 | 0.1 |
| RC2 / LeastFlicker+LowCpu | 91 | 4.08 | 29.3 | 42.7 | 61.2 | 0 | 1294 | 0 | **35.1** |

Reading the table honestly:

* **Fastest** is the profile for raw latency — no consumer hop, no barrier
  — at the cost of *every* edit being a visible backspace+retype
  (10 696 retypes; this is the "original OpenKey feel").
* **Least Flicker** gets **zero** visible retypes and one commit per burst,
  and pays for it with the highest consumer CPU and the worst tail under a
  saturating unpaced burst (the TSF path serialises everything, and the
  simulated commit is charged at 3 µs each — 9396 of them). It is the right
  choice for editors that flicker on SendInput, not for a latency contest;
  the report says so and so does the settings UI note.
* **Max Correctness** has the *best* burst p99.9 of the ring-based profiles
  (56 µs) because batch=1 keeps every barrier wait short (p99 50 µs vs 1.1 ms
  for Balanced's 32-edit batches); its price is more commits and dictionary
  lookups (+20 % consumer CPU).
* **RC2 Balanced vs RC1 default**: barrier timeouts 1144 → 66 and p99.9
  5.6 ms → 2.3 ms with the identical pipeline — the faster engine leaves the
  consumer more slack in a saturating burst.
* Paced runs (1000 keys/s + word pauses, `profiles_paced.log`) rank the
  profiles the same way; absolute numbers there are noisier because the
  pacing loop spins the producer core on a 2-vCPU host, and are reported
  but not used for claims.

**Benchmark gaming check:** the harness charges every profile the same
simulated commit cost, uses the same corpus and seed, and the RC1 row is
the RC1 engine + RC1 wrapper source compiled from the frozen tree. Nothing
in `Strategy` is read by the benchmarks except through the same setters
the app uses.

## 6. Optimizations tried and rejected (with numbers)

| candidate | measured | why rejected |
|---|---|---|
| **Unbounded undo history** (`kMaxHistory = 1<<30`, "avoid the erase entirely") | 98 ns/key vs RC1 113 (`tput_exp1`) — slower than the 64-ring (63) and grows memory for the whole session | Ring is faster *and* bounded |
| **`-O3` for the product** | 58.7 vs 63.3 ns/key (−7 %) | Product ships from MSVC/MinGW CI with its own flags; a −7 % micro gain on one compiler is not worth diverging release flags in an RC; bench flags left untouched per methodology rule |
| **`-march=native`** | 60.4 ns/key (−5 %) | Not shippable (per-CPU binary) |
| **Removing `engineMtx` (lock-free engine access)** | uncontended lock cost inside the 28 ns timer floor | Risk (UI thread settings writes) without measurable gain |
| **Replacing the consumer `std::function` callback + per-event QPC** | est. < 50 ns of a ~30 µs hop | Invisible in E2E; deferred |
| **Skipping `repScratch` copy when the decision is DoNothing** | already zero-length (no copy happens) | Not a bottleneck after inspection |
| **Pipeline redesign (batching wakes, futex-per-item)** | — | Out of scope: RC1 report's pipeline hypotheses H4–H7 were disproven; RC2 keeps the pipeline byte-identical and makes it *tunable* instead |
| **Raising the default spin cap to 200 µs** | Fastest/LeastFlicker profiles show the wake gain | Costs idle CPU for every user; exposed as a profile, not a default |
| **Lowering the default barrier budget to 500 µs** | more barrier timeouts in Balanced bursts | Exposed via Fastest only |
| **`checkSpelling` memoisation by word prefix** | prototype was decision-identical but +2 % slower on the mixed corpus (hash + invalidation on every backspace) | No gain |

## 9. UX: intelligent notifications & QuickTelex detector

`src/core/Notifications.hpp` (pure std, no Win32; unit-tested):

* **NotificationCenter** — stable ids, confidence threshold per id, per-id
  cooldown, per-hour cap, global 60 s gap, dedup of the pending slot
  (stronger wins), session mute, **persisted "Don't show again"**
  (`NotifySuppress_<id>` DWORD under the app registry key via an injected
  `Store`). Producer side is a single lock-free packed-atomic slot; the UI
  polls `takePending()` once per second → **zero work on the input path**.
* Policies: QuickTelexUnwanted ≤ 2/h, 30 min cooldown, conf ≥ 75;
  TsfSlowDowngrade ≤ 1/h; BarrierTimeouts once per session;
  HookReinstalled ≤ 3/h, 10 min cooldown. Verified over a simulated 3 h
  worst-case flood: 6 / 3 / 1 / 9 presentations (caps hold).
* **QuickTelexDetector** — general heuristic over *all* quick-Telex pairs
  (`cc gg kk nn qq pp tt` → `ch gi kh ng qu ph th`), not `pp` only. Model:
  expansion arms; backspace *into* the expansion + re-type / raw replace /
  engine Restore = confirmed undo (+weight); word commit = acceptance
  (−weight); window + expiry; ≥ 3 undos in 10 min and confidence ≥ 75
  raises. 0 false raises on 400 × 5 legitimate quick-Telex words; raises on
  a dozen `app / ppt / http` undo loops; no re-presentation inside cooldown.
* **Presentation** — tray balloon; click → `MessageBox` **Yes = Turn off
  quick Telex** (saved), **No = Keep**, **Cancel = Don't show again**
  (persisted). Balloon timeout/hide = dismissed (cooldown applies). If the
  shell refuses balloons the raise is dropped silently — never retried on
  the hot path. Settings tab exposes a "Thông báo thông minh" toggle.

## 12. Known limitations / follow-ups

* Everything Windows-runtime (real flicker, TSF commit cost per app,
  balloon behaviour on Windows 11 toast policy) is verified by compile +
  design here and must be exercised on the CI Windows job / a real machine
  before RC2 → Stable.
* The profile benchmark's TSF commit is a constant 3 µs; real apps range
  from 50 µs to several ms, which makes Least Flicker's relative cost
  app-dependent (that is exactly what Adaptive's slow-TSF signal is for).
* `Adaptive` battery detection uses `GetSystemPowerStatus` once per tick;
  no measurement of its effect on real battery life was possible here.

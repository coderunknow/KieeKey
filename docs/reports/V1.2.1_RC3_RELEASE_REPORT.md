## 4. Optimization kept — bucket-indexed consonant scans

**Bottleneck:** both table walks in `checkSpelling` visit every row
(33 leading, 11 end) for every call, although ~90 % of rows can never
match the word's first letter under the active option masks.

**Evidence:** §3 (checkSpelling still #1 after RC2's own pass); the row
tables are constexpr literals (`FlatTables.hpp`), so the reachable
first-letter sets per mask combination are compile-time knowledge.

**Hypothesis:** indexing rows by the word's first letter — per option-mask
combination — cuts the visited rows to ≤ 4 (leading) and ≤ 3 (end) with
zero semantic change.

**Change (`src/core/TextEngine.cpp`):** a constexpr
`ConsonantRowBucket` builder maps each letter A–Z to the subset of rows
whose first cell can equal it under (maskA, maskB), in table order. Four
leading tables (maskA ∈ {0, kEndConsonantMask} × maskB ∈ {0,
kConsonantAllowMask}) and two end tables (endMask on/off). `static_assert`
guards bucket width.

**Equivalence proof (also embedded in the source comments):**
* a row outside the bucket is exactly a row the RC2 loop rejected at its
  cell-0 comparison (or earlier, as too-short) — skipping it cannot change
  which row first wins, and the winning row returns the same `j`;
* on total rejection the RC2 loop always finished at the FINAL table row
  (single-cell `J|kEndConsonantMask`), which either wins (returns 1) or
  leaves `j = 0` — since nothing won, the identical exit value is `j = 0`,
  which is what the bucket version returns;
* the end scan's accept test (`j >= tailLen`) is kept verbatim; `j` is dead
  after that loop (verified against every later use).

**Verification:**
* `diff_engine_ab` vs frozen RC1 engine: seeds 20260904 / 777 / 31337 /
  99991 → **4 802 206 events, 0 mismatches**, 9 170 mid-stream option
  switches total; the option matrix randomizes exactly the three flags that
  select the bucket tables.
* `gate_correctness`: 2 059 419 events, 0 mismatches, 0 stale, 0 drift.
* Full native suite: 21/21 PASS (includes `test_key_correctness`'s 18 278
  exhaustive 1–3-letter sequences, `edge_behaviors`, `dirty_input`,
  `real_passages`, `stress_rc2`, `mega_correctness` paths).
* Output sink on the 20 M-key driver: **byte-identical** (3327073 both
  sides).

**Measured:** §3 table + §7 micro/percentile A/B.

**Risk:** low — pure lookup restructuring, no new state, no threading, no
allocation; decision-identity proven four ways.

**Decision: KEEP.**

## 5. Bug fixed — PendingEditCounter underflow (P1)

**Found by:** re-running the RC2 release gate (`tests/run_all_tests.sh`)
on this host — `soak_pipeline` FAIL, 5/5 runs.

**Root cause:** `PendingEditCounter::consume()` / `rollback()` used a bare
`fetch_sub`. `forceQuiesce()` — the lifecycle recovery that fires when a
drain is genuinely wedged (engine switched off, foreground auto-excluded,
power resume; RC2 calls it after two bounded drain attempts fail) — stores
0 **on the lifecycle thread**. The consumer can be mid-batch at that
moment: it already popped n edits from the ring, has applied them through
a (slow) TSF commit, and is about to call `consume(n)`. The subtraction
then wraps:

```
0 - n  →  4 294 967 29x   (read as "hugely pending")
```

**Consequence chain (all in the shipped Windows pipeline, same call shape
as the soak harness):**
1. the wrapped value is ≠ 0, so `releaseIfDrained()` never notifies the
   barrier — it stays armed;
2. every following pass-through keystroke's `waitDrained()` on the hook
   thread burns the full barrier budget (1–4 ms profile-dependent) and is
   counted as a barrier timeout → **per-keystroke latency spike**;
3. the degraded key is delivered anyway (documented degradation) →
   **pass-through keys can overtake the edits still in flight** (ordering
   violation), exactly the symptom family the class was built to prevent;
4. the count oscillates near 2³² and only recovers at the NEXT lifecycle
   quiesce — i.e. until the user switches the engine off/on again.

**Fix (`src/core/win32_wrapper.hpp`):** `consume()`/`rollback()` now go
through `releaseClamped(n)` — a CAS loop that subtracts `min(n, cur)` and
clamps at zero, atomically. A concurrent `publish()` that slips between
the load and the store is carried into the CAS retry instead of being
overwritten (a `fetch_sub` + conditional-store fixup would lose it).
`forceQuiesce()` semantics are unchanged.

**Regression coverage (permanent):**
* `tests/test_lifecycle.cpp` **case 7** (new): (a) deterministic —
  `publish(3) → forceQuiesce() → consume(3)` must leave pending at 0
  (RC2 left 0xFFFFFFFD); same for `rollback`; barrier must report drained.
  (b) hammered — a real consumer thread racing `forceQuiesce` every 25
  publishes; the counter must never report a wrapped value and must return
  to zero.
* `tests/soak_pipeline` (the gate that caught the bug) — now PASS 10/10,
  `maxPending` pinned at the legitimate bound (ring capacity + one batch)
  in every run even with forced quiesces 0–4 per run.

**Soak `barrier timeouts` note (honesty):** RC2's failing runs aborted at
~1.2 M iterations (the bound check breaks the loop), so its 3–8 timeout
counts are not comparable to RC3's full-2 M runs (3–15). Those timeouts
are the harness's own lifecycle-drain waits on a 2-CPU host, not
underflow-amplified — the underflow's signature would be a timeout on
every subsequent keystroke, i.e. thousands, not a handful. No claim is
made from these numbers.

## 6. Test-robustness fix (product code unchanged)

`tests/test_lifecycle.cpp` case 6 asserted "the 1 ms barrier budget always
suffices" — a **host-scheduling** claim, not a barrier-mechanism claim.
On this shared 2-CPU VM, the freshly created consumer thread can be
descheduled past the entire budget: **2 failures / 15 runs on unmodified
RC2 code** (and 1/10 with the RC3 code — same noise, not a regression).
The shim's own `waitDrainedHooked` rationale documents precisely this CI
flake mode. Case 6 now keeps the strict mechanism assertions (count
released; a waiter after the drain returns immediately) and reports
budget-elapsing trials as a host-slowness count instead of failing:
**0/12 failures after the change**, host-slow trials 0–1 per 200.

**Regression investigation (§26, the p50 rows):** the p50 deltas
(+0.37–0.66 µs) are 8× the engine's total share of this pipeline
(~0.05 µs). A two-run interleaved verification round was executed and the
sign of the p50 difference **inverted between runs** (v1: cur faster by
0.18 µs; v2: base faster by 0.03 µs) — the p50 difference is host
scheduler noise on the timer floor, not a change effect. The correlated
signals all point the other way: p99 improved on every metric, tail wake
−38.5 %, lag spikes −14.3 %, throughput +3.8 %. Verdict: **UNCHANGED at
p50 within host noise; tails improved.**

**Interpretation (§29, mandatory honesty):** the E2E shim on this host is
bounded by its timer/scheduler floor (~9.5–10.5 µs p50) — the engine's
0.05 µs share cannot move it, and RC3 does not claim it does. On real
Windows the engine runs on the consumer thread inside the same budget
math: a −29.5 % CPU-per-keystroke reduction is a real efficiency/battery
win and removes engine compute as a latency contributor for burst typing,
but the user-visible E2E effect depends on the Windows scheduler/TSF path
this environment cannot measure. The e2e gates (`p50 ≤ 2.5 µs`) remain
host-capability verdicts (rc=1 both sides, exactly as in RC2's own runs
on this host class).

## 9. Compatibility & lifecycle

No Windows-runtime validation was possible on this host (no cross
toolchain — **NOT EXECUTED, not marked PASS**). What RC3 does NOT change
by construction: engine semantics (decision-identical, §4), options,
profiles, output encodings, the wake protocol, the hook contract, TSF
composer, UI. The only pipeline change is the counter clamp, which
tightens an invariant (pending can never read as a wrapped value) and
releases the barrier MORE often (when a clamped release drains) — never
less. Lifecycle drains (`drainPendingEditsForHook` /
`drainPendingEditsForLifecycle`) are untouched; the quiesce contract is
unchanged and now actually holds under the race it documents.

## 10. Remaining bottlenecks (honest list)

1. `checkSpelling` is still the #1 function (12 ns/call): the remaining
   cost is the vowel scan + `kVowelCombine` matching — sequential tone-bit
   logic where restructuring risk exceeds the gain (rejected, §4.1).
2. `pushTypingState`/`saveWord` double copy — ~0.08 ns/key amortized.
3. E2E on Windows: the real gap is scheduler wake + TSF commit latency —
   not measurable here; the profile system (RC2) is the shipped lever.
4. The engine lock (uncontended) — RC2 rejected lock-free; no new evidence.

## 12. Engineering assessment

RC3 is a small, high-confidence release: one real pipeline bug (found by
refusing to wave the RC2 gate's failure away), one optimization that
attacks the profile's #1 function with compile-time evidence and
four-layer identity proof, and two hygiene closes (version carrier,
flaky-by-host gate). Engine CPU per keystroke drops 23–46 % across
workloads with byte-identical output; the pipeline's boundedness
invariant now actually holds under the exact race its documentation
described. What RC3 deliberately does not do: claim E2E wins it cannot
measure, force micro-gains where the profile says the remaining cost is
structural, or touch the Windows-only surfaces without a toolchain to
verify them.

## 1. Audit of the previous benchmark corpus (done first, no tuning)

The existing corpus was audited before any v1.2.0 work and again for this
release. Findings that shaped this report's methodology:

1. **Invalid percentiles in `imebench_kit/harness/bench_perf.cpp` (v1.1.x).**
   `Stats::percentile()` indexed the **unsorted** sample vector (`p50 = ns[idx]`
   with no `std::sort` anywhere), and `max` was `ns.back()` of the unsorted
   vector. Every p50/p90/p99/p999/max previously emitted by that harness was
   therefore arbitrary, not a percentile. Fixed in the v2 harness: samples are
   sorted before quantiles, min/max from the sorted ends (§5).
2. **Cross-workload state carry-over + no warm-up (v1.1.x perf harness).**
   One engine session ran all four workloads back-to-back (2M keys each) with a
   single `startNewSession()`; the first CPU-cache warm-up and any pending
   composition state leaked between workloads and runs. v2 resets the session
   per workload and discards a 200 000-key warm-up first.
3. **Single-run, printf-only output (`tests/e2e_bench.cpp` v1.1.x).** No
   repeat runs, no machine-readable artifact, no way to show run-to-run spread.
   v2 adds `--runs=N` and `--json=` with per-run records.
4. **No timing-overhead floor reported anywhere.** Per-key `steady_clock`
   (`qpcNs()` = `steady_clock` ns — the POSIX clock used by the whole shim
   corpus is `std::chrono::steady_clock`, wrapped under the QPC name) costs
   ~20–25 ns per call on this host — comparable to the measured engine decision
   (~100–150 ns). v2 measures a `T0-control` no-op loop on the same timer and
   reports it separately (never subtracted silently).
5. **Tail metrics on a shared host are scheduler-dominated.** p999/max move by
   ±50–100% between otherwise identical runs on both sides. Prior reports
   printed single-run tails as if stable; this report prints every metric as
   *median over N interleaved runs* with the run spread.
6. **`bench_tone_latency.cpp` self-gates correctly** (aborts on composition
   drift against frozen expectations) and its per-pop key streams are a sound
   deterministic workload — kept unchanged apart from the version label.
7. `tests/bench_three_engines.cpp` (optional external comparison, §9) is
   unchanged from the lineage and was re-run for this release.

No audit finding was used to tune the engine toward the benchmark; §5–§8 report
what the hardened harnesses actually measure on the actual v1.1.3 vs v1.2.0
binaries.

## 2. What v1.2.0 changes (engine diff = `faf76ab..4c2258d`, 2 files)

* `EngineOptions::macroExpandsOnPunctuation` (new, **default false**): when
  enabled, printable macro-break punctuation typed as `Char` (`, . ; / ' \ - =`)
  expands the pending abbreviation *and* stays visible (`xl,` → `xin lỗi,`),
  and the macro-key accumulator resets so consecutive `xl, xl,` both expand.
  The legacy default keeps OpenKey-2.0.5 semantics byte-for-byte (trigger
  swallowed, poisoned accumulator blocks the next match) — verified by the
  differential gate and the mega harness (§4).
* `macroExpansionUtf16` now renders through the VIQR pipeline when
  `OutputEncoding::Viqr` is selected (precomposed Vietnamese no longer leaks
  as raw Unicode into pure-ASCII VIQR output).
* Grammar-gate fast path: a `wordHasTransform_` eligibility flag lets the
  engine skip the per-key `checkGrammar()` re-scan for words that never
  received a transform (provably no-op; monotone within a word, conservative
  on restore). This is the change the latency A/B in §5–§7 quantifies.

## 5. Micro layer — engine decision latency (`imebench_kit/harness/bench_perf.cpp` v2)

Method: 2 000 000 keys per workload per run, 200 000-key warm-up discarded,
session reset per workload, per-key `steady_clock` ns, sorted percentiles,
T0-control no-op loop for the timer/loop floor, 6 interleaved A/B runs per
side (seeded workload-order shuffle per run). Compiler: identical `-O3
-DNDEBUG` on both sides. Full decile+tail distributions are recorded per run
in the JSON (`results/perf_*.json`; `schema: bench_perf.v2`).

T0-control floor: **~23–24 ns** mean per sample on **both** sides (identical
timer; max ~50–62 µs = scheduler hiccups, reported not hidden).

min–max in parentheses):

| delete | 123 (122–124) | **102** (102–103) | **−17.1 %** | 150 | 221 | 114.5 |

`T1+encode` (decision + `replacementUtf16` render):

| Workload | v1.1.3 p50 | v1.2.0 p50 | Δ p50 |
|---|---|---|---|

Reading: the p50 deltas are far outside the run spread (spread ≤ 4 ns on
p50). The speedup concentrates exactly where the grammar-gate predicts it:
no-transform work (`passthrough`, `delete`) gains ~15–18 %, transform-heavy

improvements; `delete` is the one workload where v1.2.0's tail is consistently
lower (p99 220–222 vs 240–260). Mean is lower on v1.2.0 for all 8 cells.
Context: a 200 WPM typist produces one key per ~58 ms; 102–137 ns/key is
0.0002–0.0003 % of the human-typing budget.

## 8. Validity & falsification checks

* **Timer overhead:** T0-control no-op loop = 23–24 ns/sample on both sides,
  identical within noise; reported separately, never subtracted. Timer =
  `steady_clock` (vDSO, ~ns resolution); its overhead is ~20 % of a ~120 ns
  decision, which is why §5 claims rest on p50 *deltas* (engine work only)
  plus identical overhead on both sides, and on mean/p90 as cross-checks.
* **Percentile math:** v2 sorts before quantiles (the v1.1.x bug, §1.1).
* **DCE:** control loop uses a volatile sink; engine results are consumed
  through `replacementUtf16` (the shipped consumer contract), so no measured
  call is dead code.
* **Ordering bias:** interleaved A/B; per-run seeded shuffle of workload order.
* **Cache state:** warm-up per workload on the same session before measuring;
  sessions reset per workload.
* **Falsification (correctness):** the §4 gate FAILs on a deliberately broken
  engine and the tree was re-verified clean afterwards.
* **Falsification (workload→engine):** the tone bench aborts on composition
  drift; the gate's S1 asserts keygen-keystroke streams reproduce the composed
  source exactly (Telex+VNI) so every typed-workload latency run is anchored to
  correct engine output.

## 9. External-engine comparison (optional)

The vendored three-engine comparator (`tests/bench_three_engines.cpp`,
`tests/run_three_bench.sh`) was re-run for this release on the same host and
interleaved methodology (2 000 000 keys per engine, per-key `steady_clock`;
KieeKey v1.2.0 = this release, built from this tree; OpenKey 2.0.5 and UniKey
= the unmodified vendored references through their Linux adapter paths):

| engine | mean ns | p50 | p90 | p99 | max ns |
|---|---|---|---|---|---|
| KieeKey v1.2.0 | 208 | 176 | 284 | 589 | 3 382 154 |
| OpenKey 2.0.5 (legacy, vendored) | 294 | 230 | 425 | 1 018 | 3 033 298 |
| UniKey 4.x UKEngine (vendored) | 122 | 105 | 149 | 220 | 479 816 |

All three include the same ~20–40 ns per-sample timing overhead, so the
relative ranking is exact. KieeKey is ~29 % faster than the OpenKey engine it
descends from but ~44 % slower than UniKey on this workload set. This is an
illustrative, adapter-mediated comparison, not a product claim: the vendored
engines run through their Linux adapter paths with their as-shipped
configurations, and per-engine differences in the workloads' restore policy
(the comparator documents KieeKey's dictionary-restore marking non-Vietnamese
words raw where the legacy defaults mark them) mean the ranking conflates
engine internals with intentional rule differences. The comparator also
re-documents two pre-existing defects in the unmodified vendored references
(UniKey's fixed 128-entry word buffer overflow on >11-letter words; OpenKey
2.0.5's `checkForStandaloneChar` OOB read at `TypingWord[_index - 1]`) that
are deliberately left unpatched to keep the references pristine.

## 10. What cannot be measured on this host (explicit, not fabricated)

The Win32 product surfaces — real SendInput/registry paths, TSF against a real
text store, the WinUI-3 settings UI, elevated-app handling, and end-to-end
latency through the real Windows input stack — **cannot be measured on this
Linux KVM host** and are not assigned numbers here. The deterministic shim
(§6–§7) measures everything the pipeline owns above the OS; the real-Windows
sign-off procedure is `docs/reports/VERIFICATION_PROTOCOL.md`. No benchmark
result in this report was adjusted, filtered, or re-run until a desired answer
appeared; every table reports medians with spreads, and the run artifacts
(§11) contain the full per-run data.

## 11. Reproducibility & machine-readable output

with the documented flags, writes the environment record, runs the
correctness gate (and aborts if it fails), then runs the micro / integration /
tone layers for `--runs=N` interleaved runs and aggregates everything into

## 12. Verdict

* **Correctness:** v1.1.3 and v1.2.0 both pass CTest 3/3 and the 2.06M-event
  differential gate; the new macro option's default keeps 2.0.5 parity.
* **Performance:** engine decision p50 improves **−5 to −18 %** by workload
  (largest on no-transform work, consistent with the grammar-gate change);
  shim-pipeline burst p50 **−8 %**; tone populations **parity**; paced
  mixed-passage delivery lower on v1.2.0. Tails within run-to-run spread
  (reported with spreads, not claimed).
* **Regressions:** none measured. One non-reproduced 0.315 µs tone outlier on
  v1.2.0 reported above.
* **Limitations:** Windows-only surfaces and the 2.5/7 µs burst gates are
  unmeasurable on this host and are explicitly not assigned numbers; the
  Windows procedure is VERIFICATION_PROTOCOL.md.

The two P1s are both **silent-corruption / silent-deadlock** classes that no
error message, log or crash would ever have surfaced:

* **P1-a — IME process could die mid-keystroke.** Any exception escaping the
  consumer handler (`std::bad_alloc` under memory pressure is enough) called
  `std::terminate()` inside a `noexcept` frame. The user's IME disappears
  while the tray icon stays behind. → fault isolation + a diagnostic counter.
* **P1-b — `resumeFromText()` inflated the backspace clamp: silent data
  loss.** Caret-moving keystrokes (arrows, Home/End, PgUp/PgDn, Ins,
  Ctrl+Backspace) and every mouse click queue a resync. Each one replayed the
  visible word through `process()` and counted every replayed letter as newly
  committed, inflating `visibleAccount_` by `k × len(word)`. That counter is
  the **only** clamp on how many characters a correction may delete, so a
  later edit could delete text to the LEFT of the word that the engine never
  committed — with no error anywhere. Repro: click into a partially typed
  word, press Right a few times, finish the word.

## 1. Method (as mandated)

1. **Understand the whole system first.** Full read of the input pipeline
   (`ModernKeyHook` → SPSC ring → consumer thread → `TextEngine` →
   `OutputItem` ring → TSF/inline commit), the app lifecycle
   (`src/app/main.cpp`), `win32_wrapper.hpp`, `ProcessMonitor`,
   `TsfComposer`, and the config/registry path. Mental model built for
   startup → init → idle → key → composition → commit → app switch → config
   change → shutdown, plus the abnormal paths (input during init, rapid app
   switching, sleep/resume, lock/unlock, DPI/display change, config change
   while active, shutdown during input, typing during background activity).
2. **Frozen baseline established before touching anything** — see the
   baseline report.
3. **Deep stability audit** — concurrency, state management, input handling,
   focus/app switching, startup/shutdown (§2).
4. **Graceful recovery** — the lifecycle drain (poke → bounded wait → forced
   quiescence) replaces every bare "wait for the barrier" call (§2, D1).
5. **Edge-case testing** — fuzz (1M keys), soak (200k engine / 1.28M
   transport), plus the new state-transition matrix (§3).
6. **Memory/resource stability** — RSS sampling in both soaks, no growth.
7. **Release gate** — §5.

**Explicitly not done:** no optimization for its own sake, no risky rewrite
for a small gain, no change to the engine's composition semantics. The only
engine change in this release is a **correctness** fix to the backspace
clamp.

## 2. Issues found and fixed

Severity: **P0** = data loss / crash / unusable · **P1** = user-visible
failure with no obvious cause · **P2** = degraded but recoverable ·
**P3** = cosmetic / hygiene.

### P1-a — An escaping exception killed the IME process *(P1, crash)*

**Where:** `ModernKeyHook::consumerThreadMain()`, which is `noexcept`.

**Root cause:** the consumer handler runs real work — TSF edit sessions,
`std::wstring` payloads, COM calls. Any exception escaping it reached the
`noexcept` boundary and called `std::terminate()`. The most likely trigger is
plain `std::bad_alloc` under memory pressure, i.e. exactly when the machine is
already struggling.

**Why it matters more than it reads:** an IME is a *singleton system
service* through the user's fingers. If it dies, every window keeps
accepting keystrokes and produces **raw, uncomposed Vietnamese**. The tray
icon stays in the notification area, so there is no visible signal. The user
concludes "KieeKey broke again".

**Fix:** the handler call is wrapped in `try/catch (...)`; one bad event is
dropped and counted (`ModernKeyHook::handlerExceptionCount()`), and the
pipeline keeps running. Dropping one edit is strictly better than a dead IME.

**Evidence:** `tests/test_lifecycle.cpp` case 4 — a consumer that throws on
one item keeps draining the remaining 999, the pending count returns to
zero, and conservation holds (`applied + faults == published`).

### P1-b — `resumeFromText()` inflated the backspace clamp → silent data loss *(P1, data loss)*

**Where:** `TextEngine::resumeFromText()` / `TextEngine::process()`.

**Root cause:** `resumeFromText()` replays the visible raw word through
`process()` under a `rawReplay_` flag. `process()`'s consumer-visible
accounting block executed `++visibleAccount_` for every `DoNothing` `Char`
— **including the replayed ones.** Those letters were already on screen
(already accounted for, or belonging to document text this engine never
committed).

A resync is queued on **every** caret-moving keystroke and every mouse
click, so after `k` arrow presses inside a word of length `n` the counter
could be inflated by `k × n`.

**Why it is data loss:** `visibleAccount_` is the **only** clamp on
`backspaceCount` (the D2 over-backspace policy). An inflated clamp lets a
later correction delete characters to the LEFT of the word — text the engine
never committed — silently, with no error, no log, and no way for the user to
attribute the damage to the IME.

**Repro (minimal):**
```
type "cha"        → visibleAccount() == 3
resumeFromText("cha") → visibleAccount() == 6   ← BUG (doubled)
type "o" + space  → correction deletes 6 chars, not 4
```

**Fix (two lines + comment, in `src/core/TextEngine.cpp`):**
1. `process()` early-returns `if (rawReplay_) { finalizeResult(); return
   result_; };` **before** the accounting block — replayed letters are never
   counted as newly committed.
2. `resumeFromText()` ends with `visibleAccount_ = rawWord.size();` — the
   engine then owns exactly the adopted word, which is the exact upper bound
   on any legitimate backspace.

**Evidence:**
* `/tmp/probe_resume` before: `vis=3 → 6`. After: `vis=1 / 3 / 4` (correct).
* `tests/test_state_transitions.cpp` property **P3** is a dedicated
  regression test: 500 consecutive `resumeFromText` calls plus 2000
  interleaved type/resync/arrow iterations must keep `visibleAccount()`
  bounded by the word length.
* **Negative control run:** reverting the two lines makes the suite fail with
  `consumer would underflow the document — bs=3 doc=2 vis=4`, i.e. the test
  genuinely catches the bug rather than passing vacuously.

### P1-c — "Typing `p` twice turns it into `ph`": quickTelex fired at any word position *(P1, false positive)*

**User report:** *"Sometimes, when I type 'p' or other keys 2 times, it will
become another key, for instance, 'p' when type 'pp', it becomes 'ph'."*

**Where:** `TextEngine::isQuickTelexKey()`, used by `handleQuickTelex()`.

**Root cause:** the eligibility test was

```cpp
index_ > 0 && (c=='C'||c=='G'||c=='K'||c=='N'||c=='P'||c=='Q'||c=='T')
           && chr(index_-1) == c
```

— i.e. "the key equals the last character of the pending word", **at any
position**. That is byte-identical to upstream OpenKey 2.0.5
(`tests/reference/openkey-2.0.5/engine/DataType.h:147`), so this is an
*inherited* defect, not a KieeKey regression. With "gõ tắt" enabled, `kQuickTelex`
maps `CC→CH, GG→GI, KK→KH, NN→NG, PP→PH, QQ→QU, TT→TH`, so every word containing
a doubled consonant was silently rewritten:

| typed | got | | typed | got | | typed | got |
|---|---|---|---|---|---|---|---|
| `happy` | `haphy` | | `apple` | `aphle` | | `letter` | `lether` |
| `account` | `achount` | | `running` | `runging` | | `success` | `suches` |
| `tattoo` | `tathoo` | | `supper` | `supher` | | `copper` | `copher` |
| `attitude` | `athitude` | | `button` | `buthon` | | `cc` | `ch` |

**Why it is wrong (not merely surprising):** Vietnamese is syllabic. Every
cluster in that table is **syllable-initial**, and no Vietnamese syllable
contains a doubled consonant. The transform can therefore only ever be
*correct* at the start of a word — everywhere else it is pure corruption, and
it is invisible to the user until they read the text back (there is no error,
no log, no visual cue at the moment of typing).

**Fix:** require the doubled pair to be the word's first two letters.

```cpp
index_ == 1 && (c=='C'||c=='G'||c=='K'||c=='N'||c=='P'||c=='Q'||c=='T')
            && chr(index_-1) == c
```

**Feature preserved, 100%:** because the clusters are syllable-initial, every
legitimate use of the option has the doubling at position 0. Verified:
`ppongf→phòng`, `ccaof→chào`, `kkongf→khòng`, `qqan→quan`, `nnuw→ngư`,
`ttooi→thôi`, `ttieeng→thiêng`, and `ppongf ccaof→phòng chào`.

**Evidence:**
* `tests/test_key_correctness.cpp` case 1 pins **37 real words** byte-for-byte;
  case 2 pins the 11 legitimate expansions.
* **Negative control:** reverting `index_ == 1` to `index_ > 0` makes the suite
  fail with `happy -> haphy`, `apple -> aphle`, `letter -> lether`, … — the
  test is not vacuous.
* Case 4 exhaustively checks all **18 278** one-to-three-letter lowercase
  sequences for silent character loss (0 failures).

### P1-d (test fidelity) — the state-transition suite modelled the wrong consumer

Found while building the harness for P1-c. The `Consumer` in
`tests/test_state_transitions.cpp` applied `EngineResult::backspaceCount`
**unconditionally**. The shipped hook does not: `src/app/main.cpp` only
applies an edit when the result is *consumed*, and for the grammar-repair path
— a `DoNothing` result that nevertheless carries a non-zero `backspaceCount` —
it deliberately discards the edit and lets the key through. The model was
therefore emitting `work → ửokk` where the real IME emits `work → ửok`, and
`test → étt` where the real IME emits `test → tét`.

The model now reproduces the shipped rule line-for-line (see the comment at
the top of `tests/test_key_correctness.cpp`). The suite still passes all
**15 877** checks under the corrected model, so the invariants it asserts were
never dependent on the bug — but any future absolute-text assertion in it
would have been wrong.

### P2 — Stranded pending-edit count: a 1 ms stall on every keystroke *(P2, smoothness)*

The pending-edit counter that gates the ordering barrier could stay armed
forever when the producer stopped queueing work — engine switched OFF,
foreground app auto-excluded, pipeline restarted, power resume. Nothing
wakes the consumer, the count never reaches zero, and **every** following
pass-through keystroke pays the full 1 ms barrier budget before being
delivered late (and out of order).

**Fixes, in three parts:**
* `PendingEditCounter` was **extracted out of `src/app/main.cpp` into
  `win32_wrapper.hpp`** so the invariants are unit-testable on every
  platform (it is pure `std` + the barrier; no Win32).
* `ModernKeyHook::pokeConsumer()` — wake the consumer from **any** thread
  (`SetEvent` is thread-safe and idempotent for a manual-reset event).
* `drainPendingEditsForLifecycle()` — **poke → bounded wait → poke → bounded
  wait → `forceQuiesce()`** replaces every bare `waitPendingEditsDrained()`
  at a lifecycle point. `forceQuiesce()` is documented as safe *only* where
  the caller guarantees no further edit can be published (engine off), and
  is the recovery for a genuinely wedged consumer (e.g. a TSF edit session
  marshalled into a hung application's STA).

### P2 — Dropping the wake signal *(P2, correctness)*

`ModernKeyHook::enqueue()` dropped the newest event on ring overflow — and
with it the wake. But the `KeyEvent` payload is only a *signal*: the real
work (an `OutputItem`) was **already** pushed into the app's out-ring and
already published into the pending count. Dropping the wake strands that
edit. Overflow now always wakes (`::SetEvent`), counted in
`overflowWakeCount()`. Costs one syscall in a situation that only arises when
the pipeline is already deep in a backlog; correctness wins.

### P2 — Data race on the pump-tick callback *(P2, use-after-free)*

`stop()` on the detach path assigned `pumpTick_ = nullptr` — a **non-atomic
write to a `std::function`** that the pump thread may be reading at that very
moment (torn read of the callable's state = use-after-free of its captures).
Replaced with an atomic `pumpTickDead_` flag that the pump checks *before*
invoking the callback.

### P2 — Data race on the hook-installation handshake *(P2, UB)*

`start()`'s polling loop read the `keyboardHook_` RAII handle member, which
the **pump thread** writes. Benign on today's x86/ARM, but it is undefined
behaviour and would fail any future TSan build. Replaced with an atomic
`hooksInstalled_` flag, published once after all three hooks are set, and
**re-armed in `start()` and cleared in `hookThreadMain()`'s exit path** so a
stop/start cycle can never observe a stale "installed".

### P2 — Version-bearing singleton / wake names *(P2, upgrade hazard)*

`kSingletonMutexName = L"KieeKey_1.1.0_Singleton"` and
`kWakeEventName = L"KieeKey_1.1.0_Wake"`. Two real consequences: mixed
version identifiers in the shipped binary (this was the *only* place still
claiming 1.1.0), and a genuine **upgrade hazard** — the moment the name
changed, a running OLD instance and a newly launched NEW one no longer share
a mutex, so **both start, both install a low-level keyboard hook, and every
keystroke gets composed twice.** Now version-free (`KieeKey_Singleton`,
`KieeKey_Wake`), and `scripts/check_version.py` enforces that they stay so.

### P2 — Stale hook thread id after shutdown *(P2)*

`hookThreadId_` was not cleared on the pump thread's exit path, so a later
`stop()` could `PostThreadMessage(WM_QUIT)` to a thread id that is already
gone — and thread ids are recycled, so `WM_QUIT` could land on an unrelated
thread. Cleared alongside `hooksInstalled_`.

### P2 — Producer-side fault isolation *(P2)*

The hook producer callback now isolates exceptions too, and sets a deferred
repair flag so the pipeline is repaired on the next loop instead of being
left half-updated.

### P3 — Power / session / display lifecycle *(P3 → real-world UX)*

The app ignored `WM_POWERBROADCAST` (suspend / resume automatic / resume),
`WM_WTSSESSION_CHANGE` (lock, unlock, fast-user switch, remote
connect/disconnect) and `WM_DISPLAYCHANGE`. Every one of those transitions
can drop low-level hook callbacks, lose a key-up, change the DPI or the
monitor topology, or change the foreground without a usable
`EVENT_SYSTEM_FOREGROUND`. The state carried across a resume used to be
whatever happened to be cached:
* tracked Shift/Ctrl/CapsLock bits (a modifier released while the secure
  desktop owned the keyboard is never seen as a key-up);
* the cached keyboard-layout HKL;
* the per-app exclusion and TSF-vs-inline policy for a foreground that no
  longer exists.

All three messages are now handled: on resume / unlock / display change the
engine session is reset, the modifier tracker is re-seeded, the HKL and the
exclusion policy are re-probed, and (for display change) the settings dialog
is re-scaled if it is open. `WTSRegisterSessionNotification` is registered at
startup and unregistered on teardown, and the `PBT_*` codes are
locally `#define`d so the file still builds against an older SDK.

### P3 — DPI: the settings dialog only resized its frame *(P3)*

`WM_DPICHANGED` resized the frame and left every child control and font at
the old DPI — text clipped, controls misplaced, sometimes off-dialog. Now
`refreshSettingsDpi()` + `rescaleChild()` re-scale every child (position,
size **and** font) at the new DPI, driven by a **per-DPI font cache** that
**never evicts an in-use font** (the previous cache deleted fonts that were
still attached to live controls).

### P3 — Stale single-instance state on shutdown *(P3)*

`clearRunningPid()` / teardown now leave no stale state behind, so a crash
or a force-kill cannot make the next launch believe an instance is running.

### P3 — Foreground probe race *(P3)*

`probeForegroundResponsiveness()` could act on a probe whose foreground had
already changed again. The probed HWND is now carried in `wParam` and
validated before use.

### P3 — Version-identifier hygiene *(P3)*

Six stale carriers (`scripts/*`, `imebench_kit/harness/*`, the WinUI about
banner, `THIRD-PARTY-NOTICES.md`) plus a duplicated CHANGELOG heading. All
fixed, and `scripts/check_version.py` now gates them.

## 4. Performance vs the frozen baseline

### 4.1 Methodology correction (important)

The first A/B run showed `mixed / T1-decision` **p99 at +58 %** (225 → 356
ns). That number is **an artifact and is retracted**. Comparing a *frozen
binary built from the old tree* against a *newly built binary from the
current tree* measures code-layout variance as much as it measures the
change: rebuilding the **current** tree with the two TextEngine lines
stripped out (call it **V0**) already reproduces the new numbers.

| mixed / T1-decision p99 | value |
|---|---|
| frozen baseline binary (`d2453db`) | 225 ns |
| **V0** = current tree, fix removed | 357 ns |
| **V1** = current tree, fix shipped | 354 ns |

The +58 % was build-to-build layout noise, not a regression. **The
authoritative comparison is therefore the same-tree A/B below.**

V0 = v1.2.0 Stable with the two `visibleAccount_` lines removed.
V1 = v1.2.0 Stable as shipped. Min of 3 runs each, 2M keys per run.

| passthrough | T1+encode | 143 ns | 143 ns | **0.0 %** | 268 ns | 268 ns | 0.0 % |

## 6. Developer workflow speed

The user reported waiting **1 733 s** for a single command. Two distinct
causes, both fixed; neither touched a benchmark's meaning.

### 6.1 `tests/run_all_tests.sh` — 84 s → 35 s (17 targets)

Two real defects, not just missing parallelism:

1. **`--jobs` was parsed but never used.** Every build and every run was
   strictly sequential, so ~45 s of independent compiler work was serialised.
   Builds and runs are now recorded as job scripts and dispatched with
   `xargs -P "$JOBS"`; results are printed afterwards in declaration order so
   the report stays stable and readable.
2. **`src/core/TextEngine.cpp` was recompiled 13 times.** It is the dominant
   translation unit (~1.7 s of the ~2.5 s each target costs). It is now
   compiled **once per language dialect** (C++23 for the modern harnesses,
   C++17 for the differential harnesses that also link the vendored C++11-era
   OpenKey 2.0.5 sources — exactly the pair the script already used) and
   linked. ~22 s of pure waste removed.

### 6.2 `tests/bench_tone_latency.cpp` — 866 s → 134 s default

Profiling showed the runtime was **independent of `--iters`** (100 iterations
took the same 866 s as 2 000), which pointed at the `mixed` population: it
types a real passage at a **real typing pace** — it sleeps between keystrokes,
which is precisely the point of a paced simulation, so its cost is
wall-clock-bound. Measured per cell:

| pace | per (path × barrier) cell |
|---|---|
| 80 wpm | ~26 s |
| 150 wpm | ~14 s |
| 250 wpm | ~8.3 s |

The exhaustive matrix was 3 paces × 3 reps × 3 paths × 2 barriers = 54 cells
≈ 14.5 minutes. The default is now the two bookend paces at one rep (~2 min);
**`--fast`** gives one pace and one rep (~50 s) and **`--full`** restores the
complete matrix for a release run. `--help` documents all three. Nothing about
the measurement changed — only how many cells are measured by default.

### 6.3 Net effect

| Command | Before | After |
|---|---|---|
| `bash tests/run_all_tests.sh` | 84 s (16 targets) | **35 s** (17 targets) |
| `./ok_tone_bench` (default) | 866 s | **134 s** |
| `./ok_tone_bench --fast` | n/a | **~50 s** |
| `ctest` | 3 targets | **15 targets, 13 s** |

> **Platform split.** The 15 ctest targets above are registered on the **Linux**
> build, where every harness compiles and runs. On **Windows** only the three
> suites the CI workflow has always documented — `ok_tests`, `ok_ring_tests`,
> `ok_wrap_tests` (plus the `ok_version_check` script gate) — are registered by
> default. The eleven extended harnesses are opt-in there via
> `cmake -S . -B out -DKIEEKEY_BUILD_EXTRA_TESTS=ON`. See **D-6**.

## 7. Remaining / deferred issues

| ID | Issue | Severity | Why deferred |
|---|---|---|---|
| **D-1** | The optional **WinUI 3 front-end** (`KIEEKEY_BUILD_UI=winui3`) does not use the pending-edit counter / drain barrier — its `commit()` path has the same ordering exposure the Win32 app had before this release | P2 | It is **opt-in and not built by CI** (it needs the Windows App SDK NuGet package restored on the build machine), so any change there would ship **uncompiled and untested**. Adding untested concurrency code to a target that cannot be built is a worse trade than documenting it. Its user-visible version string was corrected. |
| **D-2** | `tests/test_lifecycle.cpp` and `tests/soak_pipeline.cpp` model the Win32 `SetEvent`/`WaitForSingleObject` wake pair with a condvar. A PASS there proves the **protocol**, not the Win32 calls that implement it | P2 (test fidelity) | The Win32 halves (`ModernKeyHook`, `src/app/main.cpp`) cannot execute on the Linux CI host. Sign-off on real Windows remains a manual step (see `docs/reports/VERIFICATION_PROTOCOL.md`). |
| **D-3** | Host noise on the shared CI sandbox is ±60 % at p99, which makes sub-microsecond comparisons uninformative | P3 | Structural. Mitigated by (a) same-tree A/B, (b) min-of-N-run reporting, (c) the T0 no-op timing control in the micro harness. |
| **D-4** | No automated real-Windows UI test (DPI change with a physical display switch, UAC elevation, secure desktop) | P3 | Requires an interactive Windows session; the code paths are covered by inspection and by the portable lifecycle suite. |
| **D-5** | The engine's D2 over-backspace policy has exactly one clamp (`visibleAccount_`). It is now correct and regression-tested, but it remains a single point of failure | P3 | Adding a second, independent clamp would change composition semantics — out of scope for a stability release. **Recommended for v1.3.** |
| **D-6** | The eleven extended harnesses are **not** built by the Windows CI job by default (`KIEEKEY_BUILD_EXTRA_TESTS`, default `OFF`) | P2 | Several are POSIX-dependent (`gate_correctness.cpp` installs a `SIGBUS` handler; `soak_engine.cpp` reads `/proc/self/status`), and none had ever been compiled by MSVC. Because `cmake --build` builds every defined target, registering them broke the build on **all three** CI platforms under `/W4 /WX`. The POSIX dependencies have been fixed and all eleven now cross-compile for Windows, but they remain opt-in until they have been verified green under real MSVC. Enabling the flag is the porting checklist. |

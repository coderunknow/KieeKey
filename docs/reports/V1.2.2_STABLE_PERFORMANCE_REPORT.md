# KieeKey v1.2.2 Stable — Performance Report

Campaign: **v1.2.2 Stable** over the qualified RC4 tree (`8ad5739`, tag
`v1.2.2-RC4`). This campaign ran on an **independent host** from every
previous v1.2.2 campaign. Raw artifacts:
[`docs/bench/stable-122/`](../bench/stable-122/); environment capture:
[environment.txt](../bench/stable-122/environment.txt).

**Headline:** the engine hot path and every shipped source file are
**byte-identical between RC4 and Stable** (the release diff is version
identity + release evidence only), and the measured binaries are
**section-for-section identical** (`.text`/`.rodata`/`.data` SHA-verified
below). Every strict RC4→Stable delta is inside this host's measured noise
band; the decision-relevant metrics are flat. Versus **v1.2.1 Stable**, the
1.2.2 line is **−8.6 % on the throughput floor** with **byte-identical sink
digests**. Verdict: **NO REGRESSION — NO OPTIMIZATION REQUIRED.**

---

## 1. Host and methodology (frozen for all three-way comparisons)

* Host: Debian 12 (bookworm), 2× Intel Xeon @ 2.60 GHz (shared VM),
  4.0 GiB RAM, CPU governor not exposed (container) — full capture in
  `stable-122/environment.txt`.
* Compiler/toolchain: g++ 12.2.0 (Debian), CMake 4.4.3 + Ninja (pip),
  Zig 0.16.0 (pip `ziglang`) for the Windows cross-build gate.
  **This is NOT the RC4-campaign host** (that was Debian 13 / g++ 14.2 /
  MinGW-GCC 14): every number from that host is labeled
  HISTORICAL / NOT STRICT below and is never compared as a strict delta.
* Trees: `base-121` = pristine `v1.2.1-Stable` (`715c527`), `base-rc4` =
  pristine `v1.2.2-RC4` (`8ad5739`), Stable = the final release tree.
* Harness: `tests/run_bench_suite.sh --ab-base=…` — the harness sources
  (`gate_correctness.cpp`, `bench_perf.cpp`, `e2e_bench.cpp`,
  `bench_tone_latency.cpp`) are **SHA-synced from the current tree into the
  base tree before building**, so both sides run identical harness code;
  interleaved run order; identical flags per layer
  (`-O2 -DNO_205` gate / `-O3 -DNDEBUG` perf / `-O2` e2e / `-O2` tone).
* Throughput floor: `tests/bench_tput_floor.cpp` (versioned driver) copied
  byte-identically into each tree's build, 20 000 000 keys, mode 1,
  interleaved passes, sink digest recorded per run.
* Engine-decision latency vs full E2E latency are reported **separately**
  (micro layer vs integration layer) and never mixed.

## 2. Strict v1.2.1 Stable ↔ RC4 ↔ Stable — the comparison set

### 2.1 Engine throughput floor (20 M keys, STRICT, interleaved)

| | v1.2.1 Stable | RC4 | v1.2.2 Stable | Δ RC4→Stable | Δ 1.2.1→Stable |
|---|---:|---:|---:|---:|---:|
| ns/key (median of 3) | 79.58 | 72.71¹ | 72.75¹ | **+0.06 %** | **−8.61 %** |
| per-run spread | 79.50–81.46 | 71.91–74.72 | 71.83–74.07 | — | — |
| sink digest | 2905520108639366859 | 2905520108639366859 | 2905520108639366859 | **identical** | **identical** |

¹ RC4/Stable medians over all 8 interleaved pairs (5-pair session + 3-pair
session). The sink digest is identical on **every single run** and across
**all three versions** — the 20 M-key computation is decision-identical.

An early 3-run window showed RC4→Stable at +1.17 % (just over the 1 %
policy line). Investigation per policy §8: (a) the `TextEngine.o` sections
are SHA-identical between RC4 and Stable (§4), so no code mechanism exists;
(b) an **A/A control** (the same RC4 binary run twice per interleave, 5
passes) swings −2.6 %…+4.4 % paired on this host
([floor_rc4_vs_stable.txt](../bench/stable-122/floor_rc4_vs_stable.txt));
(c) across all 8 A/B pairs the deltas flip sign (+1.17, −0.84, +2.73, −1.69,
−3.12, +0.28, −3.26, +1.92 %). Conclusion: **not reproducible; sampling
noise; NOT a regression.**

| peak RSS MB | 8.445 | 8.723³ / 8.496⁴ | 8.465³ / 8.476⁴ | STRICT within a session |
| IME pipeline footprint MB | 5.97 | 6.24³ / 6.02⁴ | 5.99³ / 5.99⁴ | STRICT within a session |

³ session 1 (1.2.1↔RC4↔Stable suite sessions, 3 interleaved runs/side).
⁴ session 2 (5 additional interleaved RC4↔Stable pairs). E2E latency
medians are only comparable **within one interleaved session** on this
host — this VM's run-to-run band for E2E latency is large and was measured
directly:

**A/A control** (the *same* RC4 binary, twice per interleave, 5 passes —
[aa_control_noise_band.txt](../bench/stable-122/aa_control_noise_band.txt)):
paired hot-p50 deltas **−9.0 %…+16.2 %**, pipeline/raw p50
**−10.7 %…+21.0 %**, while **throughput stayed within ±0.7 %**. Session 1
showed Stable "+19.7 %" on hot p50 medians; session 2 showed Stable
"−7.1 %" — the sign flips between sessions and every delta sits inside the
A/A band, so the E2E latency deltas are **host scheduler noise, not code
effects** — and the code-identity proof (§4) makes a code effect impossible.

* E2E p99.9: raw p99.9 143–151 µs (121↔RC4 session); burst/hot p99.9 ~85–93 µs
  across sessions — same A/A-band caveat.
* Wake/pay p50: 39.4 µs (1.2.1) vs 41.2 (RC4, session 1) vs 38.3↔44.8
  (RC4↔Stable sessions) — inside the band.
* Lag spikes: RC4 135–429 keys, Stable 267–580 keys per 100k run — host
  deschedules (the harness counts them explicitly); not an engine metric.
* The burst-mode absolute gates (p50 ≤ 2.5 µs, p99 ≤ 7 µs — defined for the
  real-time Windows path) are not met on any side on this shared VM: a
  **host-capability verdict**, identical for all three versions (rc=1
  recorded, suite does not treat it as failure).

### 2.4 Tone-population latency

`ok_tone_bench --pop=all --path=inline`: composition validation
**8/8 populations OK on every side** (self-gated every run). Per-population
medians in the suite summaries
([suite_121_vs_rc4/](../bench/stable-122/suite_121_vs_rc4/),
[ab_rc4_vs_stable_micro_tone.txt](../bench/stable-122/ab_rc4_vs_stable_micro_tone.txt)):

shows 1.2.2 faster on most populations (e.g. d-bar 0.284→0.190 µs) and
slower on the synthetic `mixed` population (8.45→9.98 µs, a known artifact
of the RC2 option-precedence branch on that stream).

## 3. Historical context (NOT STRICT — different host/compiler)

## 4. Binary-identity proof (RC4 ↔ Stable)

`TextEngine.cpp` / `win32_wrapper.cpp` / `e2e_bench.cpp` compiled with
identical flags from both trees: `e2e_bench.o` **byte-identical**;
`TextEngine.o` and `win32_wrapper.o` `.text`/`.rodata`/`.data` sections
**SHA-identical** (whole-file differences are non-code metadata only).
The measured code is the same code; combined with the A/A control band
this closes the regression question with evidence rather than assertion.

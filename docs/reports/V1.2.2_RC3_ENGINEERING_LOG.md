## 3. Initial pipeline measurement (before any optimization)

Measured the full shim chain: hook pump → producer decision → SPSC ring +
auto-reset event wake → consumer → `TextEngine::process` →
`replacementUtf16` → `InlineEmitter` → target. Two wirings exist in the code:

- **production**: Win32 app registers a producer handler; pass-through keys
  are counted (`countPassThrough`) and never wake the consumer. This is the
  shipped wiring — and the RC2 e2e archive did NOT model it (the archive's
  tool modeled the *all* wiring).
- **all / consumer-callback-only**: every key rides wake→consumer (the
  WinUI-3 front-end uses this; no producer handler is registered).

Cost attribution (RC3 final, production wiring): p50 0.183 µs, p95 0.594 µs,
p99 0.980 µs, p99.9 55.0 µs — with 38–63 keys per 100 k in contiguous
scheduler-deschedule events (0.038–0.063 %). Engine decision alone is
0.067–0.27 µs p50. **The dominant cost in the shipped wiring is the OS
scheduler, not the IME.** In the consumer-callback wiring the dominant cost
is the wake→consumer hop: p50 ~27–30 µs, wake-pay p50 42–45 µs — the exact
numbers the RC2 archive reported as "the pipeline".

**Finding that reframed the KPI table:** the RC2 report's e2e numbers
describe the all-wiring. The shipped path (already in bc0a20a) is the
production wiring. The RC3 campaign therefore added a `--model=production`
mode to `tests/e2e_bench.cpp` (schema v3; p95 added in v4) rather than
optimizing a path the app doesn't run.

## 4. Candidate optimizations — hypothesis → A/B → verdict

### 4.1 Raise adaptive spin cap 100 → 1000 µs (rejected)

- Hypothesis: the consumer parks between word bursts; a bigger spin budget
  keeps it hot and cuts the edit-path p99.9.
- Baseline: production wiring, default cap (200 µs effective budget),
  100 k keys × many runs (see rc3-pair/ and final/).
- A/B: `final/e2e-v4-prod-spin100-{1..3}.json` vs
  `final/e2e-v4-prod-spin1000-{1..3}.json`, 100 k keys each.
- Result: raw p99.9 49.4 → 18.8 µs, burst-hot p99.9 19.2 → 3.6 µs; p50/p95/p99
  within ±10 %. The improvement is real and repeatable on this workload.
- **Why rejected:** the gaps the bigger cap bridges are 300–800 µs — the
  bench's word-burst convention, not human cadence (150 WPM = 48 ms gap ≫
  1 ms cap). At human cadence the consumer is parked in both settings; the
  paced runs (`rc3-pair/e2e_prod_paced*`) show no such trade, and their
  p99.9 (47.5–95.8 µs) is dominated by the pacing-sleep CPU-wake artifact.
  CPU: production wiring mean 5.7 % → 6.0 % (peak 39.7 % both) — no saving at
  the lower cap either; consumer-callback (WinUI) wiring peak 59.6 % →
  139.0 % (2.3×).
- Rollback criterion (pre-registered): any A/B that worsens p99/p99.9 beyond
  host noise → reject; any optimization whose gain is confined to non-human
  cadence → reject. Both hit. **Do not raise the cap.**

### 4.2 Lower spin cap 200 → 100 µs (rejected)

- Hypothesis: save CPU without tail loss.
- A/B: `final/e2e-v4-prod-*` (default 200) vs `final/e2e-v4-prod-spin100-*`.
- Result: CPU identical (mean 5.7 % vs 5.7 %, peak 39.7 % both); tail equal
  or worse (burst p99.9 17.7 vs 19.2 µs).
- **Rejected** — no energy win, no tail win.

### 4.3 All-model spin-cap A/B (bench artifact, not a production lever)

`rc3-pair/e2e_spin100/200/1000.json` show spin1000 turning the whole chain
into a ~0.7 µs p50 — but only because the consumer never parks across the
bench's 80 ms pauses. Not applicable to any shipped wiring; documented so a
future reader does not "discover" this gain a second time.

### 4.4 Queue/wake/batching/copy elimination (not applied)

- The shipped wiring never wakes the consumer for pass-through keys
  (~99.9 % of keystrokes), so there is no queue-hop cost to remove there; the
  consumer path is already woken only for edits, and batching is already
  per-edit (`InlineEmitter` one SendInput per edit).
- `emitMtx` (win32_wrapper.cpp:67) serializes emit vs TSF; it is required by
  the documented ordering contract and was measured uncontended (tone t2
  p50 0.36 µs). Removing it would trade correctness for nothing.
- **Not applied** — no measured contention.

### 4.5 Any TextEngine change (not applied)

The engine object in RC3 is byte-identical to RC2 (only version constants in
`kieekey_core.hpp` changed; `TextEngine.cpp/.hpp` untouched). Decision
identity to frozen RC1 is re-proven by `diff_engine_ab` (0/1,202,051) and by
the option matrix (0 failures). Floor A/B confirms no throughput change
(§6.1). Nothing to optimize, and the mission forbids touching it without a
proven win.

## 5. Real bugs found and fixed

### 5.1 WinUI-3 front-end received NO events (critical, shipped in RC2)

- Bug: `ModernKeyHook::{keyboardProc,mouseProc,winEventProc}` used
  `producerHandler_ ? producerHandler_(ev) : ProducerDecision{}` — and
  `ProducerDecision{}` defaults to `{suppress=false, wake=false}`. The WinUI
  front-end (`src/ui/MainWindow.xaml.cpp`) registers **only** a consumer
  callback (`m_hook->start(callback)`), never a producer handler. Result:
  every event was counted pass-through, the consumer callback never ran —
  no composition, no word-break, no foreground refresh. WinUI was inert.
- Fix: the no-handler default is now `ProducerDecision{false, true}` in all
  three entry points (deliver every event to the consumer); the producer
  handler remains an optional optimization for apps that register one. The
  Win32 app is unaffected (it always registers `onHookEvent`).
- Evidence of behavior: code-level reading of all three sites; e2e `all`
  model now *is* this contract (every key rides the ring) and reproduces the
  historical all-wiring numbers; the Linux lifecycle/state-transition tests
  exercise the same state machine (24/24 PASS).
- **Not verified**: compiled in this sandbox (Windows-only source); CI's
  x64/ARM64/ARM64EC jobs compile `KieeKeyApp.exe` on the PR. WinUI 3 itself
  is never built by CI (`KIEEKEY_BUILD_UI=none`). Recorded as a limitation.

### 5.2 Option-matrix JSON truncation (harness, P2)

- `buf[128]` truncated long digest rows → invalid JSON. Fixed to
  `buf[512]`; regenerated artifacts parse as `kieekey.option_matrix.v1`.

### 5.3 Harness artifacts in tier-6 FRESH probes (not engine bugs)

Two initial "divergences" in the new torture tier were harness artifacts
(stale `tempOffEng` re-applied across flips; visibleAccount clamp for fresh
engines). Fixed in the harness; the engine was correct. Do not re-investigate
as engine bugs.
